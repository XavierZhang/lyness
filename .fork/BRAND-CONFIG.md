# 品牌与租户配置的两层划分

lyness 有两种交付形态，它们能改什么不同：

- **私有化部署**：跑在客户自己的服务器上，客户即运营方，可以完整改品牌。
- **SaaS**：跑在 lyness 的服务器上，多租户共享，租户不能改 Logo 与 favicon，其余配置有限可改。

本文定义哪些配置属于**部署层**（配置文件，部署时生效），哪些属于**租户层**（数据库，管理后台随时改），以及为什么这样分。

## 划分原则

判断一项配置该放哪层，问三个问题：

| 问题 | 部署层 | 租户层 |
|---|---|---|
| 谁改它？ | 运营方（有服务器访问权） | 租户管理员（只有后台账号） |
| 改一次影响谁？ | 整个部署 | 一个租户 |
| 改动是什么事件？ | 一次部署 | 一次日常操作 |

**二进制资产一律属于部署层。** 这不是偏好，是它消掉了一整条攻击面：资产由运营方以文件形式随部署投放，就没有上传接口、没有服务端校验、没有租户上传的 SVG 在别的租户浏览器里执行脚本的可能。

## 部署层（配置文件，仅私有化可改）

投放方式：部署脚本写入配置文件与资产目录，启动时读取，**一次生效**。

| 配置 | 形式 | 说明 |
|---|---|---|
| 产品 Logo（图标） | 文件 | 侧边栏与对话首屏，比例约 1.36:1 |
| 产品字标 | 文件 | 比例约 6.5:1；缺省则以产品名文字排版 |
| 浏览器 favicon | 文件 | 画布 1:1；SVG 可内嵌 `prefers-color-scheme` 规则自适应明暗 |
| PWA 名称与图标 | 配置 + 文件 | `manifest.webmanifest` |
| 产品名（中/英） | 配置 | 浏览器标题、界面各处 |
| 主题色 | 配置 | 注入 CSS 变量 |
| 是否显示「Powered by lyness」 | 配置 | 私有化默认关闭；SaaS 由平台侧固定 |
| 是否允许租户改品牌 | 配置 | SaaS 部署置否；私有化由运营方决定 |

**SVG 在这一层是安全的。** 上传接口不存在，写入这些文件的人是运营方本人，与写 nginx 配置同级。这正是把资产放部署层换来的收益。

### 投递机制

Web 前端由 `lyn-host-frontend-static` 提供构建产物目录，每个 index 响应都经 webserver 的 `renderIndex` 渲染，后者支持**结构化注入行**写入 `<head>`。因此 favicon 链接、页面标题与主题色变量在服务端注入，**改配置不需要重新构建前端**。

注入行的类型定义在 `packages/host/webserver/src/injections.ts`，可用 `kind` 为
`global` / `script` / `script-src` / `script-preload` / `style` / `html`。
**没有 `link` 这一种**，所以 favicon 用 `{ kind: 'html', placement: 'head', html: '<link rel="icon" …>' }`，
主题色用 `{ kind: 'style', text: ':root{--brand-…}' }`，配置对象本身用 `{ kind: 'global', … }` 交给前端读。
注入行必须是可 JSON 序列化的纯数据——同一张表要喂两个渲染器（服务端 HTML 与 static worker 部署的页面侧解释器），
这一点在设计部署配置的数据结构时是硬约束。

产品内的 Logo 走官方已插槽化的三个位（`sidebar.brand.mark`、`sidebar.brand.name`、`conversation.hero.brand.mark`），由品牌插件按部署配置填充，**零官方文件改动**。

## 租户层（数据库，SaaS 与私有化都可改）

投放方式：管理后台写入数据库，热生效。

| 配置 | 谁可改 | 说明 |
|---|---|---|
| 模型供应商白名单 | 租户管理员 | DeepSeek 是清单中的一项，不再默认 |
| 可用的生成模型（图片／视频／音乐） | 租户管理员 | 与语言模型一样按租户配置，API Key 按租户隔离 |
| 默认供应商 | 租户管理员 | 留空则强制用户在登录后自选 |
| 是否允许自定义供应商 | 租户管理员 | 对应 `llm-pi-ai` 的手写路由能力 |
| 功能授权（Agent／Skill／MCP） | 租户管理员 | |
| Agent 自我身份 | 租户管理员 | ⚠️ 模型可见，须进会话日志 |
| 界面文案覆盖 | 租户管理员 | 首屏标语、欢迎语等，见下 |
| 席位与用量配额 | **仅平台运营方** | 租户只读 |
| 计费档位 | **仅平台运营方** | 租户只读 |

租户层配置本身再分两类：租户管理员可改的，与仅平台运营方可改、租户只读的。去标（`showPoweredBy`）属于后者——若租户能自行关闭，这项就失去商业含义。

### 文案覆盖如何生效

官方词典对同一个（命名空间, 语言）只允许注册一次，重复注册抛错，所以不能直接覆盖。可行路径是**注册语言变体**：为租户注册 `zh-x-<slug>`，fallback 指向官方 `zh`，其中只写被改过的键，其余自动回落到官方文案。

该机制已在本仓库实测验证：语言变体可注册、未类型化注册接受部分键、组合后未覆盖的键正确回落。

因此 `slug` 必须满足语言标签格式：**每段不超过 8 个字符、纯字母数字**。它同时用作子域名与租户可读标识，与展示名分开（`slug: acme` / `displayName: Acme 科技有限公司`）。

## 两种形态的差异

| | 私有化部署 | SaaS |
|---|---|---|
| Logo／favicon／字标 | ✅ 配置文件改 | ❌ 固定为 lyness |
| 产品名／主题色 | ✅ 配置文件改 | ❌ 固定 |
| 供应商白名单等租户配置 | ✅ 管理后台改 | ✅ 管理后台改 |
| Agent 自我身份 | ✅ | ✅ |
| 界面文案覆盖 | ✅ | ✅ |
| 配额／计费 | 运营方即客户自己 | 仅平台运营方 |

一套代码，差异由部署层的 `allowTenantBranding` 一个开关表达，不是两份代码。

## 与需求文档的冲突

需求文档 `lyness-requirements.md` 写：

> 支持多租户独立配置品牌标识（Logo、平台名称、域名、主题色、UI 布局样式）

且验收标准第 2 条要求 `/api/v1/tenant/config` 按租户域名返回对应 Logo。

本方案与之**不一致**：SaaS 形态下租户不能改 Logo。这是有意的产品决策——完整白标成为私有化部署的能力，而非 SaaS 的租户自助项。

需求文档中「多租户 OEM 贴牌」在 SaaS 下的实际含义因此收窄为：租户可改文案、Agent 身份、供应商与功能授权，但共享部署的视觉标识。若要在 SaaS 恢复完整白标，需重新引入资产上传与校验（含 SVG 净化），并接受随之而来的跨租户攻击面。

## 对既有计划的影响

- **Phase 4 的 4.8（品牌资产上传与校验）大幅收缩**：SaaS 不需要上传接口；私有化的资产由部署脚本投放。原设计中的格式白名单、比例校验、内容寻址去重、SVG 净化取舍等，退化为部署文档中的一份资产规格说明。
- **`TenantConfig` 去掉 `markUrl`／`wordmarkUrl`／`faviconUrl`**，这些上移到部署配置。
- **新增部署配置文件**及其读取插件，属于 Phase 1 的前置。

## 部署层配置放在哪：已定（2026-09-13）

**不是 `settings.yaml`，也不是独立文件，而是组合层的插件配置。**

原先设想放 `settings.yaml`。查过上游的[配置来源归属](../.agents/notes/implemented/architecture/2026-08-04-configuration-source-ownership.md)后，
这条路是错的——解析次序是：

```
本次运行显式 > 用户设置(settings.yaml) > 组合 > 启动 shell > 发现的文件 > 默认值
```

`settings.yaml` **压过**组合。把品牌放进去，等于让使用该部署的人可以改掉产品名和图标——
而部署的标识恰恰是必须对这个人成立的事实。上游那份笔记给了对应做法：
「必须把某字段钉死在用户设置之上的部署，自带 bin 或 loader 树，或者干脆不挂设置提供方」。

因此：品牌值是 `@lyness/lyn-host-brand-deployment` 的组合层 `Config`，该插件**不注册任何设置段**，
组合应用之下的任何一层都触及不到它。部署方式是填 profile 的 `cordis.patch.yml` 并重启。

也不走构建期。上游给自己打品牌用的是 `LYNESS_CLIENT_*`（构建期嵌入浏览器产物），
换品牌就得重新构建前端，部署脚本做不到。本方案作用于每一个 index 响应。

理由与被否方案见 [Agent Note](../.agents/notes/implemented/architecture/2026-09-13-deployment-brand-as-composition-config.md)。

### 资产放置与替换步骤：已定

```yaml
# $LYNESS_HOME/profiles/<名字>/cordis.patch.yml
- id: brand-deployment
  config:
    productName: Acme Agent
    themeColor: '#1f6feb'
    assetDirectory: /srv/acme/brand     # 绝对路径，部署脚本写入
    favicon: favicon.svg
    mark: mark.svg
    wordmark: wordmark.svg
    showPoweredBy: false
```

资产**按角色寻址，不按文件名**：`favicon.svg` 以 `/brand/favicon.svg` 提供，
`wordmark.png` 以 `/brand/wordmark.png` 提供。请求不把任何路径片段带进文件读取。
可提供类型：SVG、PNG、WebP、ICO、JPEG。配置错误在**加载时**失败，部署不会带着错的品牌启动。

## AI 品牌生成工具（仅私有化部署，2026-09-15 定）

### 范围

- **只给私有化部署的运营方用**：部署时生成一次，产出部署级品牌，交给 `brand-deployment` 使用。
- **SaaS 不开放**：SaaS 租户继续使用 lyness 品牌，上文的两层划分不变。
- 不开放 SaaS 是产品决定，不是安全原因：生成出的 SVG 由平台自己描出，只含路径，不存在租户上传文件的攻击面。以后若对 SaaS 开放，前提是租户仍不能上传文件，并且要先完成 1.1、1.2、1.3、1.6，再把 `brand-deployment` 改为按请求所属租户取资产。

### 形态：`lyn` profile，不是独立命令，也不是 Web 设置页

- 仓库规定受支持的 Node 应用只能从 `lyn` 带 profile 启动（[规则](../docs/architecture.md#application-launch)），独立可执行文件会被 `verify-application-entrypoints` 拒绝。因此做成 `lyn --profile brand-studio`（名称暂定），由运营方在服务器上运行。
- 不做进 Web 应用的设置页：Web 应用的使用者不应能改部署的身份，与品牌不放 `settings.yaml` 是同一个理由。
- 上传入口同样放在这个 profile 里，不放在管理后台。上传者是有服务器权限的运营方，信任级别与手工把文件放进 `assetDirectory` 相同；上传只接受图标 PNG。

### 流程

```
图标 PNG，二选一
 ├─ 上传：按下方资产规格上传图标 PNG
 └─ AI 生成：填写品牌简介（扩展槽）→ 生图模型出 4～8 张候选 PNG → 预览挑选
        ↓
图标 PNG → 收紧画布、校验比例 → 矢量化 → 单色图标 SVG → 白名单与自动校验
        ↓
favicon SVG：由图标 SVG 补成正方形，加暗色规则

字标：品牌名 + 选定字体 → 字体排版 → 单色字标 SVG

预览确认 → 写入 assetDirectory，并生成 brand-deployment 的 patch 层 → 重启生效
```

- 运营方**只提供图标，且只接受 PNG**：不接受 SVG 上传，也不接受字标上传。
- 写入部署的每个 SVG 都由引导程序自己生成：图标和 favicon 来自 PNG 矢量化，字标来自字体排版。上传与 AI 生成两条路径在 PNG 之后完全相同。
- 取舍：已有矢量原稿的运营方也要先导出 PNG，再由程序描回矢量，精度会略低于原稿；换来的是部署里不存在任何「上传的 SVG」。

### 扩展槽：运营方填写与平台固定

填写内容**按字段填进提示词模板，不作为自由文本直接拼接**，避免一句「忽略以上要求」绕开硬约束。

| 运营方填写 | 平台固定（不可改） |
|---|---|
| 品牌英文名、中文名 | 单色、扁平、纯白背景 |
| 行业和产品，一句话，限长 | 图形比例（见下方资产规格） |
| 调性，从预设标签选 | 16px 下能认出来 |
| 设计方向 1～3 个，每个一句话，限长 | 负面词中的通用禁止项 |
| 禁止出现的元素（选填） | 输出格式与分辨率 |
| 字标字体，从预设清单选 | 提示词模板本身（运营方可在配置中调整） |

### 字标：字体排版，不用生图模型

- 上传与 AI 生成两条路径都用字体排版出字标，运营方不上传字标。

- 生图模型经常拼错字母，中文名更不可靠；字体排版拼写一定正确，结果可复现，无需人工核对。
- 用 `fontkit` 把品牌名排版并转成路径，选型经实测（见任务 1.8）。字体来源的最终决定见下方「字体」一节；中文字体体积大（`@fontsource/noto-sans-sc` 解压后 74.5MB，每个字重切成 102 个分片），不打进产品，由运营方提供完整字体文件，如思源黑体 / Noto Sans SC。

### 字体（2026-09-15 定，2026-09-16 已交付）

**范围：内置字体与品牌方自带字体都只用于品牌字标**，不涉及 Web 界面正文字体；字体只在 host 上读取，字标以轮廓形式分发，不下发任何字体到浏览器。


| 场景 | 字体来源 | 理由 |
|---|---|---|
| SaaS | **只能用平台内置字体**，租户不能提供或修改 | 产品与安全决定：租户不上传任何文件。不是许可证要求 |
| 私有化部署 | 品牌方可用 `--font <文件>` 提供自有字体，运营方须同时 `--accept-font-license` 确认其授权允许用于 logo；不提供时用平台内置字体 | 品牌方的字体是其身份的一部分 |

- **私有化自带字体不违反 OFL，也不违反商业字体许可**：字体文件只在运营方服务器上被读取，brand-studio 不复制进资产目录、不随平台分发、不修改它；产出的字标 SVG 是字形轮廓图形，不是字体软件，OFL 不约束用字体做出的 logo。字体授权是否允许做 logo 由品牌方负责，因此设确认参数。
- **平台内置字体只收 SIL OFL-1.1**：OFL 允许随软件分发和销售，只禁止单独售卖字体；分发时须附许可证全文与版权声明（进第三方声明）；有保留字体名的字体（如思源黑体保留 "Source"）若裁剪或修改，不得沿用原名，接入时逐款核对。
- **与官方的关系**：路线不冲突。上游拒绝非宽松许可时要求「审查分发条款并记录决定」。实现时发现内置字体不是 npm 依赖，上游脚本没有安放包内第三方文件的位置，因此新增「内置第三方文件」机制：各包用 `third-party-assets.json` 记录文件的来源、许可证与 sha256，生成器逐条校验，未登记的字体文件直接报错。**不**把 OFL-1.1 整体加进宽松清单。代价是改两处上游文件（`scripts/gen-third-party-notices.ts`、`lefthook.yml`），已登记 CUSTOM.md。
- **多语言不乱码**：内置 Inter SemiBold（拉丁、希腊、西里尔、越南）+ Noto Sans CJK SC Medium（中日韩，含假名与韩文），按此顺序逐字回退，共 17MB。阿拉伯文、希伯来文、泰文、印地文等仍被拒绝，需先实测从右到左与连写排版再加入。
- **已交付**（2026-09-16）：`packages/host/brand-fonts` 随附两个字体；`typesetWordmark` 收一组字体并逐字素簇回退；`brand-studio` 的 `--font` 已改为可选。[决策](../.agents/notes/implemented/architecture/2026-09-16-built-in-wordmark-fonts.md)

### 生图模型：做成能力缝，不绑定厂商

- 仓库目前没有图像生成能力（2026-09-14 检索确认），新增一条能力缝：服务定义 + 各厂商 Provider + 调用方。它是平台的通用能力，品牌工具只是第一个调用方，定位见 [TASKS.md 的 1.7 一节](TASKS.md)。上游没有对应能力，不存在路线冲突。
- **设置入口**：模型按租户配置——SaaS 与私有化部署都由租户管理员在管理后台设置本组织可用的模型；私有化部署也可以在 brand-studio 引导里完成首次设置，写的是同一份租户配置。与上游按部署存一份的做法不同，详见 [TASKS.md 的 1.7 一节](TASKS.md)。
- **未配置即不可用**：没有配置模型时，AI 生成这条路径不出现，品牌简介不会发给任何第三方；配置了模型，即表示同意把品牌简介发给所选厂商。境内部署建议只选境内模型。

推荐方向如下，具体型号与价格以接入时厂商文档为准：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 境内部署 | 通义万相（阿里云百炼）、即梦 / Seedream（火山引擎） | 数据不出境 |
| 海外，看重扁平图标质量 | Recraft | 出图风格适合扁平单色图标；本流程统一取 PNG 输出再矢量化，不直接使用模型给的 SVG |
| 海外，看重提示词服从度 | OpenAI GPT Image 系列、Google Gemini 图像模型 | 单色、比例等约束执行得好 |
| 需要多模型切换 | OpenRouter、Replicate | 一个接口接多家 |

### 矢量化与校验

依赖库（许可证核实于 2026-09-14）：

| 库 | 许可证 | 用途 | 结论 |
|---|---|---|---|
| `@neplex/vectorizer` | MIT | PNG 解码与位图描边；原生插件，预编译覆盖 macOS / Linux / Windows 等 14 个平台 | 采用；精确锁定 0.1.0 |
| `pngjs` | MIT | PNG 解码 | 不需要：描边库自带解码 |
| `imagetracerjs` | Unlicense | 位图转 SVG；2023 年后未更新 | 备选 |
| `potrace`、`esm-potrace-wasm` | GPL-2.0 | 位图转 SVG | 不采用：随私有化部署包分发会带上 GPL 义务 |
| `fontkit` | MIT | 字标排版转路径；woff、woff2、ttf、otf 均可读 | 采用；仓库 2024-08 后无新提交，属成熟停更 |
| `opentype.js` | MIT | 字标排版转路径 | 不采用：2.0.0 解析 Inter 失败（不支持第 6 类替换查找格式 2） |
| `harfbuzzjs` | MIT | 字形排版 | 不采用：读不了 woff／woff2，只认 TTF／OTF |
| `svgo` | MIT | 压缩 SVG | 采用；它不是安全过滤器 |

- **白名单检查**：由 `isBrandSvg` 按输出语法检查——只接受尺寸与 `viewBox` 一致的 `svg`、固定的暗色规则，以及只含移动、直线、曲线、闭合命令的 `path`；其他任何元素、属性、注释、声明或引用都不通过。检查对象是程序自己的输出，用来拦住描边库或后续改动带进来的意外内容。
- **自动校验**：是否单色、图形实际比例、路径数量上限。
- **交给运营方判断**：好不好看、16px 下能否认出、是否与已有商标相似。确认生效前需勾选商标确认条款。

### 资产规格

这是生成与校验的目标，也是手工制作 logo 时的要求。数值取自 0.1.5 代码实测。

| | 图标 | 字标 | favicon |
|---|---|---|---|
| 比例（宽:高） | 1:1～1.4:1，不能竖长（上游 1.36:1） | 不超过 7:1（上游 6.5:1） | 1:1 |
| 显示尺寸 | 侧边栏宽 24px，首屏宽 34px | 高 24px | 16～512px |
| 限制来源 | 组件按宽度定尺寸，侧边栏品牌行高 24px | 侧边栏最窄 264px 时字标区剩 168px，超出部分被截掉 | 浏览器标签页 |

图标 PNG 的输入要求：不小于 1024×1024，纯黑白或透明背景，图形本身（不含留白）宽高比 1:1～1.4:1。
