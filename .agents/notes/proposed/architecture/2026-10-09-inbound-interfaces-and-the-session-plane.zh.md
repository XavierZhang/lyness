# Agent Note: 活儿如何到达 agent，以及它落在的那一个会话平面

Status: proposed

[English](2026-10-09-inbound-interfaces-and-the-session-plane.md) | 中文

## Problem

进来的路已经有好几条，而每一条都自己发明了一套"到达"。

[`api/gateway`](../../../../packages/api/gateway/README.zh.md) 是 Web 与桌面客户端说的那个 Typert RPC 端点。[`sdk`](../../../../packages/sdk/README.zh.md) 是给程序用的 JSON-RPC。[`acp`](../../../../packages/acp/README.zh.md) 是另一个 agent 来驱动会话。[`webhook`](../../../../packages/webhook/README.zh.md) 把一个外部事件变成 Web 工作区里的一个根会话。[`schedule`](../../../../packages/schedule/schedule/README.zh.md) 会唤回一个冷会话，并把到期的那一次作为后续消息投递进那个会话。[钩子桥](../../../../packages/hooks/hook-protocol/README.zh.md)让外部 harness 能拦下一个提示词或附加上下文。

其中两条本来就做对了。schedule 投递进的是**原来那个**会话，并在它冷掉时唤回它；webhook 建的是一个普通的根会话，而不是某种特殊会话。所以"一切都落在同一个会话平面上"是这棵树已经半照着做、却从未写明的一条规则——也正因为没写明，照着做的那一半是被独立发现了两次。

缺的是托管客户真正需要的那部分。

**只有一个适配器，而且没有任何出厂挂载。** `webhook-github` 是唯一的供应方适配器，而 `webhook` 只出现在一个 CLI 示例和一个测试 fixture 里，不在任何服务于人的 profile 中。想让活儿从别处进来的客户，没有地方可插。

**没有任何东西把外部账号映射到人。** [行事上下文](2026-10-08-people-memberships-and-acting-context.zh.md)说的是请求在某个成员身份里行事，而[归属记的就是那个成员身份](2026-10-07-session-ownership.zh.md)。入站事件没有这样的成员身份：webhook 自己的规则是"受信任的程序化规则"，于是决定发生什么的是规则的作者，而不是这活儿是为谁办的那个人。在共享的托管基础设施上，这个权威放错了位置。

**而入站这个方向没有归属。** [默认模块笔记](2026-10-08-default-modules-and-views.zh.md)把连接器目录给了 MCP 服务器——那是 agent 去够客户的系统。反方向，即客户的人与系统把活儿交给 agent，不在那份清单里。这个遗漏就是本笔记存在的理由，而它恰恰是客户最先要的方向：他们要的是从公司已经在用的那个聊天工具里够到 agent，而不是只能从本产品自己的页面进。

## Proposal

给这个平面命名，让每一条进来的路先解析出人，并把到达时的操作限定为三种。

### 每个入站界面先解析出行事的成员身份，然后只做三件事之一

入站界面对调用方做认证，解析出该调用方所行事的成员身份，然后要么创建一个根会话，要么把一条后续消息投递进一个已有会话，要么驱动一段实时对话。没有第四种操作，也没有只属于入站的会话种类。

schedule 和 webhook 本来就是这样做的；把它写明，是为了不让下一个界面再发明第四种到达方式。

### 适配器做认证，平面做授权

webhook 的 README 本来就划了这条线——"供应方认证属于适配器包"——而它可以推而广之。适配器按该供应方要求的任何方式，证明是哪个外部账号在调用。平面决定解析出来的那个成员身份可以做什么。适配器从不决定权限，平面也从不去学某个供应方的签名方案。

### 外部账号绑定到成员身份，而绑定归组织所有

一个钉钉 userid、一个飞书 open_id，或一个 CRM 用户 id，通过组织管理员创建的绑定映射到某个成员身份。没有绑定的外部身份不能开启会话，而且拒绝要说明理由，不是把事件静默丢掉。

正是这一点让归属继续成立：会话归属于这活儿是为谁办的那个人，在他行事的那个成员身份里，与他自己打开产品时完全一致。

### 入站事件按行事成员身份的权限运行

到达的事件带的是解析出来的那个成员身份的权限预设与计划，不是规则作者的，也不是适配器的。一个创建会话的 webhook，拿到的沙箱模式与审批策略，和那个人在产品里会拿到的一样；额度用尽时，它以同样的方式停下。

### 投递沿用 schedule 已经验证过的那条路

往冷会话投递后续消息这件事已经解决了：schedule 唤回会话并追加那次到期。入站的后续投递走同一条路，而不是第二套机制。

### 最先做的适配器

出厂一个消息适配器，把这条接缝端到端验证一遍——钉钉或飞书，取决于第一个客户用哪个——而 `webhook-github` 作为第二种形态留下，即事件变成新会话。两个形态不同的适配器，是能证明"这是一条接缝而不是某一家的特例"的最小集合。

### 入站与出站保持为不同的包

客户自有的系统会以两个相反的方向各出现一次，而这两者不是一个功能。agent 去调的 MCP 服务器，带的是 agent 的凭据、跑在 agent 的轮次里、失败时是一个工具错误。来调 agent 的通道，带的是一个外部人的身份、不请自来、失败时是一次投递失败。同样的系统，不同的认证、不同的身份、不同的失败。它们不共用包，也不共用设置界面。

## Alternatives considered

**让每个界面各自处理会话。** 不引入新概念，而且现有界面本来就能用。否决：这就是今天的状态，也正是 schedule 和 webhook 各自独立摸到同一条会话规则的原因。下一个界面会摸到另一条。

**把入站通道放进连接器目录。** "客户的系统"只有一个地方，而客户也许就是这么描述的。否决：它把认证不同、身份不同、失败方式不同的两个方向并成一个，而并出来的界面还得解释自己的字段哪一半在什么时候适用。

**让每个人自助绑定自己的外部账号。** 自助，不需要管理员那一步。否决：这会让任何持有某个外部平台账号的人都能认领一个组织里的席位。绑定是组织的决定，正如它指向的那个成员身份一样。

**继续像 webhook 今天那样信任规则。** 对独立部署是对的，那里规则的作者就是运行服务器的人。在托管上否决：规则作者与"这活儿是为谁办的"已经不是同一个人，而只有后者的计划与权限才是正当的。

**做一个覆盖所有平台的通用聊天协议适配器。** 要写的适配器更少。否决：各平台在身份、话题串、附件与撤回语义上并不一致，通用层会变成一堆特例的并集，而其中每一个特例都没有归属。

## Acceptance criteria

- 每个入站界面在创建或触及会话之前先解析出行事的成员身份，且未绑定的外部身份被拒绝并说明理由。
- 入站事件按解析出的成员身份的权限预设、计划与额度运行——不按规则作者的，也不按适配器的。
- 创建根会话、投递后续消息、驱动实时对话是唯一的入站操作，且不存在只为入站而生的会话种类。
- 后续消息的投递通过 schedule 已经在用的那条路唤回冷会话。
- 至少一个消息适配器与 `webhook` 挂载在服务于人的 profile 上。
- 外部账号绑定由组织管理员创建，并对该组织可见。
- 连接器目录里不出现任何入站适配器，入站平面里也不出现任何 MCP 服务器。

## Risks

**适配器数量随客户增长。** 每个平台都是自己一套认证、身份与话题串模型，而用了没人做过的平台的客户一定会来要。接缝限定的是单个适配器的工作量，限定不了想要多少个。

**外部账号绑定是一个账号接管面。** 一处绑错，就把一个人的会话与额度交给了另一个人。它需要和"新增一名成员"同等的谨慎，因为它就是那件事。

**聊天通道的轮次模型与会话的不一致。** 并发消息、编辑、撤回与话题串，在一个 agent 轮次里都没有对应物。每个适配器都会想在本地把这件事解决掉，而这些本地解决方案正是这个平面不再是一个平面的方式。

**托管入站是一个互联网端点。** 在适配器证明其调用方之前，这个端点对任何找到它的人都可达。适配器是这个平面与开放互联网之间唯一的东西，这把重量压在了整个设计里最不起眼的那段代码上。

**三种操作也许会被证明太少。** 想编辑先前一条消息、或撤销已投递的工作的通道，三者都不符合。守住这条线是本意，而第一个真实适配器就是这条线被检验的地方。
