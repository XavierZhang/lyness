# Agent Note: 一个 bot、它所在的团队，和它说话的那个房间

Status: proposed

[English](2026-10-22-bots-their-teams-and-their-rooms.md) | 中文

## Problem

客户说「我们想要自己的 bot」，指的是三件这棵树现在做不到的事。

**bot 的性格和能力是部署期的文本。**[`persona`](../../../../packages/preset/persona/README.zh.md) 给一个 agent 它自己的系统提示词，这一行挂在某个 preset 组合里面。[`agent-preset`](../../../../packages/preset/agent-preset/README.zh.md) 以一串子插件行的形式声明那个 agent 看得见哪些工具、提示词段落和技能。[`mcp-client`](../../../../packages/mcp/mcp-client/README.zh.md) 每个外部服务器一条配置。[`skill-filesystem`](../../../../packages/skill/skill-filesystem/README.zh.md) 从目录里发现技能。它们每一个都是组合文件里的一行，而 [`agent-preset-registry`](../../../../packages/preset/agent-preset-registry/README.zh.md) 把后果说得很直白：「注册表不写声明」，新的 preset「是一个 bundle patch」。于是想要第二个 bot 的租户管理员，只能去找那个能改 profile 的人提工单。这正是[人员与准入可以在运行时维护](../../implemented/architecture/2026-10-21-runtime-people-and-admission.zh.md)之前「加一个同事」所处的位置，答案也是同一个。

**agent 之间只有一条边：父与子。**[`tool-subagent-control`](../../../../packages/subagent/tool-subagent-control/README.zh.md) 允许「任何一个确切的活动 Agent 面向它的直接可续子代理，而一个驻留的可续子代理也可以面向它的直接父代理」，`list_agents` 列的是一个父代理自己的孩子。这是委派，对委派来说是对的。但它不是两个属于同一个组织、由不同管理员配置、需要互相问点什么的 bot。那两个之间根本没有边，因为谁也没创建谁。

**而且几方坐不到一起讨论。**一个会话里只有一个 agent 和一个人。没有哪种会话能让三个 bot 和一个人轮流发言，也没有哪个操作能让这样的讨论以一份记录下来的结论收尾。

客户拿来跟我们比的那些框架，回答了第二和第三点，却跳过了这棵树上个月刚建起来的东西。CrewAI 给每个 agent 一个角色、一个目标和一段背景故事，再把它们编成按顺序或按层级运行的 crew；AutoGen 开一个群聊，由一个 manager 挑下一个发言人；MetaGPT 分配一家软件公司的角色，并在角色之间传递文档。在它们那里，一个 bot 是一个进程里的 Python 对象：它没有身份，什么都不拥有，谁拿着那个进程谁就看得见它，它也不向任何人请求许可。而这棵树有带身份的人、[由打开它的人拥有的会话](2026-10-07-session-ownership.zh.md)、[一条谁可以读哪个会话的规则](../../implemented/architecture/2026-10-19-session-visibility.zh.md)，以及[一道记进会话审计日志的人类审批闸口](../../../../packages/interaction/user-approval/README.zh.md)。把 bot 建模成进程里的一个对象，会让它成为这个产品里唯一一个没有身份、没有归属的行动者——也是唯一一条能读到可见性规则所拒绝的那些会话的路。

## Proposal

一个 bot 是组织名册里的一条记录。其余的都从这一条推出来。

### bot 是另一种人

[`managed-people`](../../../../packages/identity/managed-people/README.zh.md) 已经存着谁存在、属于哪个组织、持有什么身份。bot 以同样的方式存下来并被标明是 bot：它属于且只属于一个组织，持有一个身份，[`session-ownership`](2026-10-07-session-ownership.zh.md) 把它记为它所开启的那些会话的拥有者。租户管理员维护 bot 的地方，正是他们维护人的地方，适用同一套授权规则，包括那条不让租户管理员造出平台管理员的规则。

bot 唯一拿不到的是登录绑定。人是通过目录身份被准入的；bot 永远不是一个被验证过的主体，也没有哪个渠道可以拿出一个来。把 bot 放进同一份名册、又挡在准入表之外，正是让「加一个 bot」不会变成凭空铸造一个能登录的身份的原因。

### 它的性格和能力是存下来的，而写下的那一半优先

一条 bot 记录里存着人格文本，以及部署所允许的那些能力选择：哪些技能、哪些 MCP 服务器、哪些工具、哪个模型、哪套权限预设。挂载是从记录推出来的，就像一个配置好的登录渠道从它自己的记录推出来一样：部署说出有哪些种类，管理员说出有哪些实例。组合文件写下的那一行仍然是运维方的，在界面上改不动，因为那个文件在每次启动时都会被重新读一遍——这正是[运行时人员](../../implemented/architecture/2026-10-21-runtime-people-and-admission.zh.md)已经定下来的那条分界。

### bot 的能力是选出来的，不是写出来的

能力字段指的是部署已经挂载好的那些条目。管理员从目录里挑一个技能，从组织配置好的连接器里挑一个 MCP 服务器，从 preset 贡献的行里挑一个工具。自由文本只有人格和职责描述，别的没有。

任意的能力文本意味着管理员可以指名一个部署从未审过的插件，而一个连接器字符串就是一个带着凭据的 URL。理由和登录种类那一行存在的理由是同一个：部署说出有哪些形状，租户把它填满。

### 不能给 bot 比它的作者更多的东西

bot 以它自己的身份行动，而那个身份的上界是保存它的那个人的身份。租户管理员造不出一个能够到别的组织的 bot，也不能给 bot 一套他自己都选不了的权限预设。每一次修改都按**已存储**的记录做这项检查，而不只按提交的内容，理由是渠道服务已经记下过的那一条：否则一个管理员只要指名 id 就能把另一个管理员的 bot 据为己有。

### 团队就是谁可以问谁

团队是一个组织内部 bot 之间存下来的一种关系：一个名字、里面有哪些 bot，以及每个 bot 用作者自己的话写下的一段职责描述。成员身份就是那条边的来源。同一个团队里的两个 bot 可以互相问；只共享一个组织的两个 bot 不可以。

一个 bot 读得到队友的名字、人格、声明出来的能力和职责描述。这正是「去问那个懂的人」在没有中央调度器的情况下也能成立的原因，而且这些信息是管理员有意写上去的。

### 问不是读

一个 bot 可以向队友提一个问题。它不可以读队友的会话、列出它们，或者得知某一个会话的存在。

被问的那个 bot 在它自己的会话里、以它自己的身份、用它自己的工具作答，并且由它决定说什么。回来的是为这个问题组织出来的一个答复，绝不是一段对话记录。这是唯一安全的读法：被问的 bot 的那些会话属于打开它们的人，而[可见性规则](../../implemented/architecture/2026-10-19-session-visibility.zh.md)连那些人的同事都要拒绝。一个能读到它们的 bot，就是一条绕开产品在别处处处执行的规则的路。

一个答复仍然是一次披露，所以问题和答复都记进两边的会话，被问的 bot 的拥有者看得到别人问过它什么。

### 越线的事由人批

有三件事不归 bot 自己决定：够到组织之外、花掉超过发起这件事的那个人配额所允许的量、以及以比当前会话更强的权限预设行动。每一件都走 [`user-approval`](../../../../packages/interaction/user-approval/README.zh.md)：它已经会把一次性决定送给部署的应答方、无人应答时失败关闭、并把请求和结果记进会话的审计日志。

这个批准是向这件工作所服务的那个人要的，不是向 bot 的作者要的，因为被牵涉到配额和数据的是前者。

### 房间是一个有若干参与者和一份结论的会话

房间是一个普通的会话，它的参与者是若干个 bot 和被邀请进来的人。它由打开它的人拥有，像其他每一个会话那样存储和读取，它的对话记录就是那份记录。

有三样东西让它成为一个房间，而不是一堆 agent。一位**主持**决定接下来谁发言、以及讨论何时结束；它是部署选定的一条规则，不是某个 bot 自己的判断，因为一个自己挑自己回合的参与者，就是一个永远停不下来的参与者。一个**上界**——轮数、token、挂钟时间——不管主持怎么想都会让它结束。以及一份在结束时写下的**结论**：会话日志里一条具名的结果，由主持从说过的话里产出，这正是一个人打开房间时想要的东西。

房间里的 bot 看得见房间的对话记录，因为它正在里面发言。这不是上面那条规则的漏洞：房间是一个会话，参与者是被邀请进来的，他们看到的就是他们所参与的那一部分。

## Sequence

**先是 bot 本身。**名册记录、存下来的人格与能力选择、控制器，以及 Settings 里挨着「人员」的那一页。一个组织里的一个 bot，像任何 agent 一样被打开、被交谈。这里不需要任何新协议，而且它是客户可以单独用起来的那一半。

**然后是团队和问。**存下来的团队关系、一个 bot 读得到的队友名录、问这个操作，以及越线时的审批闸口。上面那些安全决定是对是贵，在这里见分晓。

**最后是房间。**多参与者会话、主持、上界和结论。放在最后，因为它是唯一需要前两者先存在的那一个，也是每条答复代价最高的那一个。

## Alternatives considered

**bot 就是 preset，让 preset 可以在运行时编辑。**更小：preset 注册表本来就在组合能力，给它加一条写入路径就覆盖了「自定义 bot」。否决：preset 没有组织、没有身份、没有拥有者，于是它底下的每一个问题——这是谁的 bot、花谁的配额、谁可以改它、它写出来的东西归谁——都得在名册之外再答一遍。名册对人已经把这些全答过了。

**bot 就是一种人，不另立记录。**在上一条之后很诱人：把人格存进人员记录里就完事。否决：人员记录是准入表够得到的那张表，而一张能放人格的表，就是一张管理员可以给活人挂上人格的表。把 bot 记录单独放、并且不可绑定，正是让这两者分开的那一下。

**同一个团队里就让 bot 读队友的会话。**每个多智能体框架都这么干，而且比「问」简单得多。否决：团队成员身份是 bot 之间的关系，而那些会话属于从未同意过这件事的人。这会让「把一个 bot 加进团队」变成一条读到可见性规则所拒绝的那些对话的路。

**让被问的 bot 直接把对话记录当答复。**比组织一段答复更省也更忠实。出于同一个理由否决，只是弱一级：一段提问方可以引用的对话记录就是那场对话，不管这个操作叫什么名字。

**让房间的参与者自己决定下一个谁说。**这是 AutoGen 的群聊，讨论质量确实更好。推迟：一场自己决定自己长度的讨论，没有任何部署可以设的上界，而这件事会在第一张客户账单上被发现。一位带上界的主持以后可以变聪明；一个没有上界的房间以后没法变安全。

**为 bot 之间的提问采用 A2A。**它正是为这个问题造的协议。按[代理隔离与团队](2026-10-08-agent-isolation-and-teams.zh.md)已经记下的理由推迟：在一个组织的运行时内部，这次提问并不跨进程，而在没有对端的情况下引入一个协商协议，是加了一个没有通信对象的面。某位客户的 bot 必须够到另一家厂商的 agent，才是回头看它的理由，而 subagent 那道缝就是它挂上去的地方。

## Acceptance criteria

- 租户管理员添加一个 bot、给它人格和能力、并与它交谈，全程没有编辑服务器上的任何文件，也没有重启。
- 组合写下的 bot 会被列出来，并且在界面上改不动。
- 一个 bot 的能力选择只能指名部署挂载过的条目；指名别的提交会被拒绝，并说明原因。
- 租户管理员保存的 bot，不持有、也够不到那个管理员自己选不了的身份与组织，且每次修改都按已存储的记录做这项检查。
- 没有任何登录绑定可以指名一个 bot，也没有任何渠道可以把 bot 当作被验证的主体拿出来。
- 一个 bot 可以问队友，不可以列出、读取或探知队友的会话；一个问题和它的答复记进两边的会话。
- 够到组织之外、超出发起者的配额、或以更强的权限预设行动，每一项都需要一次人类决定，无人应答时失败关闭，并记进审计日志。
- 房间在它的上界处结束，不管参与者正在做什么，并往会话日志里写下一份具名的结论。
- 以上每一条都在浏览器与桌面客户端上成立，在三种产品形态中都成立。

## Risks

**一个带身份的 bot，是一个没人以之登录的账号。**所有假定行动者是人的地方——归属展示、配额页、审计日志的读者——现在都多出了永远不会登录的行动者的行。这些界面每一处都得说清自己在显示哪一类，否则读用量的管理员不会知道那是谁的。

**问是一条披露通道，记下来并不等于给它设了界。**一个对每个问题都如实作答的 bot，会把它知道的一切泄露给任何可以问它的人。团队成员身份就是那个界，而它的好坏完全取决于写它的那个管理员。

**房间的代价是参与者数乘以轮数。**四个 bot 二十轮，就是为一份结论发出八十次模型请求，而打开房间的那个人不会估到这个数。上界是让房间付得起的东西，在讨论过程中显示剩余预算是这个功能的一部分，不是以后的精修。

**能力目录是部署方的责任，但看起来会像产品缺口。**找不到想要的技能的管理员会把它读成产品里没有，而其实是他们那套部署的组合里没有。页面必须说清这份清单从哪里来。

**租户管理员写的提示词文本会带着一个身份到达模型。**人格是自由文本，而 bot 带着真实的能力运行。顶住的是权限预设和审批闸口；人格绝不能把这两者中的任何一个放宽，而唯一不可配置的，就是这条规则。
