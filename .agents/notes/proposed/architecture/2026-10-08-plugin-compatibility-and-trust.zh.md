# Agent Note: 上游插件兼容，以及谁可以安装插件

Status: proposed

[English](2026-10-08-plugin-compatibility-and-trust.md) | 中文

## Problem

关于插件有两个今天没有答案的问题，而它们彼此拉扯。

**上游插件装不上。** 改名把每个包从 `@deepseek-ai/dsh-*` scope 改成了 `@lyness/lyn-*`。为上游 harness 编写的插件 import 的是旧 scope 下的包，并对它们声明 peer 依赖，而 [`lyn-plugin-manager`](../../../../packages/boot/plugin-manager/README.zh.md) 判断兼容的依据，正是包所声明的 LYN peers 与运行中的 LYN 版本。这里 import 与 peers 都解析不到，所以上游插件不是"没通过版本检查"，而是"根本不存在"。上游生态产出的一切，从本产品都够不着。

**插件是在宿主进程里运行的任意代码。** 安装会运行包管理器，包管理器会执行安装脚本，随后插件与其他所有行加载进同一个进程。在开发者自己的机器上，这正是它的用意。在服务多个组织的共享托管基础设施上，它就是"在别的客户的对话旁边运行任意代码"的能力。而产品把这条路摆在了明面上：它提供四种模式——Standard、PTC、Minimal 与 Creator——最后一种存在的目的就是让 agent 通过对话编写插件、添加功能或界面。`lyn-base` 把 plugin-manager 工具设为 `disabled: true`，因此默认没有任何 agent 能安装东西，但创造模式正是打开它的那个开关。

这两个问题只在托管产品里紧迫。私有部署是一个组织在自己的服务器上；桌面应用是一个人在自己的机器上。只有托管产品把多个客户放在同一个运行时之后，也只有在那里，"谁可以安装插件"才会有一个错误答案。

## Proposal

用别名层够到上游生态，而插件能做什么，取决于它在哪里运行。

### 别名层

在上游 scope 下发布一组包，内容只有一行：re-export 取代它的那个 lyness 包。上游插件的 import 与 peer 声明于是都能解析，源码一字不改即可加载。

该层只覆盖插件真正会 import 的那些包——上游面向插件作者公开的那部分表面——而不是树里全部六十余个包。一道门禁把这份清单与上游实际导出的内容比对，因为别名层跟随的是一个移动的目标：每次合并上游都可能新增、改名或撤回导出，而一个悄悄不再匹配的别名，比从未发布过更糟。

### 四种模式，其中一种不一样

产品提供四种模式。其中三种——Standard、PTC、Minimal——是从组合已经挂载的东西里挑选工具与提示词。它们改变的是 agent 够得到什么，从不改变运行时里有什么，也不往进程里带入任何代码。

创造模式是例外，整个信任问题都落在它身上：它存在的目的就是让 agent 编写并安装插件。把四种模式一视同仁，正是会让托管产品失守的做法；而把创造模式当成"多几个工具"，是要避免的误判。

### 插件可以装在哪里，由谁来装

- **桌面端与私有部署**——不变。运行服务器的人就是承担风险的人，四种模式全部可用。
- **托管产品，默认**——组织只能从平台审核过的目录安装。不提供创造模式，因为它产出的东西没有安全的运行之处。
- **托管产品，已购买创造模式**——该组织获得自己的运行时，创造模式在那里运行。被售卖的正是这层隔离；没有它，这个能力根本无法提供。

### 组织写的插件属于该组织

在一个组织内部编写的插件，只对该组织的成员可见，并且只有在某位成员**安装之后**才对这位成员生效。在那之前它是该组织持有的一个候选：已编写、可见、但不为任何人运行。一位成员的试验不会改变另一位成员的 agent。

组织此后可以把自己写的插件开放给其他组织，办法是上架到插件市场。上架是一次**有自己审核的、刻意为之的操作**，不是"写了插件"的自动结果；市场上承载的内容，与托管组织可安装的任何东西按同一标准审核。售卖是在此之上的商业安排，不改变信任规则：已上架的插件在任何其他组织能够够到它之前，先经过审核。

### 由运行时决定，而不是由目录界面决定

插件能否安装，在**执行安装的地方**检查，而不是在提供它的页面里。没有自己运行时的托管组织，即便直接调用该操作也无法从目录之外安装；而 plugin-manager 工具保持停用，除非启用它的那份组合是平台放置的。

## Alternatives considered

**每个包都以两个 scope 发布。** 兼容最彻底，也没有单独的一层要维护。否决：它让六十余个包的发布面翻倍，并把上游品牌重新引回产品自己的依赖图——而改名刻意移除的正是它。

**只支持 lyness 原生插件。** 最省事，没有移动目标要跟踪。否决：它放弃了上游生态，而那恰恰是保持与上游兼容的主要理由。

**安装时改写上游插件。** 可以用 codemod 在安装过程中改写 import。否决：它编辑的是作者仍在维护的第三方代码，而被改写的那一份，其作者既无法复现也无法调试。

**在共享基础设施上为插件加沙盒以提供创造模式。** 比一个组织一个运行时便宜。暂时否决：插件是一个 Cordis 行，拥有与其他所有行同等的触达范围，在共享进程内约束单独一行，远比给组织一个独立进程更大工程。而按租户分运行时本来已因其他理由成为既定决策。

**让组织内编写的插件一次性对全组织生效。** 作者少走几步。否决：一位成员的试验会改变每位同事的 agent，而第一个坏插件会放倒整个组织，而不只是一个人。

## Acceptance criteria

- 一个未经修改、import 了别名表面的上游插件可以安装并加载。
- 别名清单与上游表面不一致时，门禁失败。
- 没有自己运行时的托管组织不可使用创造模式，且该限制在**执行安装处**生效，而不是靠隐藏控件。
- 组织内编写的插件对其他组织不可见，对尚未安装它的本组织成员不生效。
- 上架市场是一次独立的、带审核的操作，市场插件在通过审核之后才能到达其他组织。
- 桌面端与私有部署保留全部四种模式。

## Risks

**别名层跟随的是别人的决定。** 表面由上游拥有，本产品只是镜像。每次合并都是镜像走样的机会；门禁能发现不一致，却无法决定该怎么办——那仍是每次合并时的判断。

**审核过的目录只和审核本身一样可靠。** 把信任边界移到审核上，就让审核成了安全控制。审核查什么、由谁执行，是本笔记不设计的工作。

**按组织分配运行时改变成本模型。** 创造模式从一个功能开关变成一个背后有基础设施的产品。定价低于该成本，每一单都是亏损。

**市场插件挂着平台的名字。** 从市场安装的客户，无论插件是谁写的，都会向平台追究。审核、下架路径，以及正在运行被撤回插件的组织如何处置，都需要在市场开张之前有答案。
