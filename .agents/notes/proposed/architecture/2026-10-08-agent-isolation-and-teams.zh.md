# Agent Note: agent 运行在什么里面，以及 agent 之间如何协作

Status: proposed

[English](2026-10-08-agent-isolation-and-teams.md) | 中文

## Problem

"每个 agent 运行在自己的沙盒里"并不是这棵树当下的事实，而一旦多个客户共用基础设施，这句话与实际机制之间的落差就要紧了。

实际存在的是一套文件作用策略。[`sandbox/`](../../../../packages/sandbox/README.zh.md) 组约束的是**子进程执行**：命令以 `read-only` 运行、只能写会话工作区之下、或者不受约束地运行，而 `lyn-base` 默认钉的是 `workspace-write`。它约束的是一条命令能碰文件系统的哪些地方。它不是一个 agent 与另一个 agent 之间的边界，也不是一个客户与另一个客户之间的边界：被约束的命令仍然跑在宿主上，以宿主的用户身份，用宿主的网络。

agent 之间同样没有分隔。[`subagent-fork-in-process`](../../../../packages/subagent/subagent-fork-in-process/README.zh.md) 派生的子 agent 按设计就运行在父进程中，并以父 agent 已完成的轮次作为起点——正是这一点让委派足够轻，也让子 agent 看得见自己要接着做的那部分工作。

对话也是存在一起的。[`session-persistence-jsonl`](../../../../packages/session/session-persistence-jsonl/README.zh.md) 为所有会话文件接收一个必填的 `root` 目录，SQLite 查询后端接收一个数据库。一个运行时服务多个组织，就会把每个客户的对话放进同一棵目录树、同一个索引，而它们之间唯一的东西，是一条每次都必须写对的查询条件。

于是托管产品缺的是三种不同的边界，而把它们统称为"沙盒"，恰好掩盖了它们需要不同机制这件事。

还有一个缺口属于这里，因为下文的计量依赖它：[`packages/llm`](../../../../packages/llm/README.zh.md) 只服务一家供应方。其中每个适配器都是 DeepSeek——共享的 Messages 传输、API key 与账号两种认证插件、模型目录——另有一个 `llm-pi-ai`。传输层走的是 Anthropic Messages 协议，而 `DEEPSEEK_BASE_URL`、`DEEPSEEK_MODELS` 与 `DEEPSEEK_MAX_TOKENS` 可以把它改道，所以某个部署可以替换成一个兼容端点。不存在的是树里的第二个供应方族，而那才是"组织自带模型"真正需要的东西。

## Proposal

三条边界，各自落在真正撑得住它的那一层。

### 一个组织一个进程

一个运行时服务一个组织。它的会话、它的存储、它的工作区与它的凭据都属于这个组织、不属于别人，而分隔靠的是操作系统，不是一条查询条件。两个毫无共享的组织，不共享任何进程。

[插件信任](2026-10-08-plugin-compatibility-and-trust.zh.md)里"按组织分配的创造模式运行时"由此成为可能，而不是第二套机制：买了创造模式的组织，就是其运行时同时接受自家插件的那个组织。

### 团队也是一个进程

组织之下的单位是**团队**：一个主 agent 加上它创建的子 agent。团队跑在一个进程里，正因为如此，子 agent 才能以父 agent 已完成的轮次为起点，父 agent 也才能直接收集结果。子 agent 并不与父 agent 隔离——这是委派的用意，不是疏漏。

所以"一个 agent 一个进程"指的是一个团队一个进程。不创建子 agent 的 agent，就是一个人的团队。

### 命令进容器

就"一条命令能做什么"而言，进程边界不是操作系统边界：被约束的命令仍然拥有宿主的网络和宿主的内核。命令执行迁入容器，容器的文件系统就是会话工作区，容器的网络是该组织允许的那些。既有的文件作用策略在容器内部继续生效——它回答"这条命令可以碰什么"，容器回答"什么是根本够得到的"。

正是这条边界让 `tool-bash` 可以提供给托管客户。没有它，约束就只是一条"请求命令自己的进程予以尊重"的策略。

### agent 之间用已经存在的协议协作

三个常被混为一谈的问题，在这里有三个不同的答案：

- **agent 够到工具或数据源**，是 MCP。仓库已经挂载了 `mcp-resources`，而接到客户自有系统的连接器是 MCP 服务器，不是插件。
- **一个 agent 驱动另一个 agent 的会话**，是 ACP。[`packages/acp`](../../../../packages/acp/README.zh.md) 是服务端——外部程序通过标准协议创建、恢复、关闭 lyness 会话——[`subagent-acp`](../../../../packages/subagent/subagent-acp/README.zh.md) 是客户端，把工作委派给在自己子进程中、拥有自己运行时、会话、模型与工具的 ACP agent。
- **在一个团队内部**，什么协议都不用：subagent 接缝就是直接的进程内委派。

团队内部在进程内协作。团队之间走 ACP，而这也正是 lyness agent 够到非 lyness agent 的方式。于是协议边界与进程边界彼此吻合：凡是跨进程的，都跨 ACP。

**A2A 刻意不采用。** 它回答的是另一个问题——不同厂商的 agent 如何彼此发现并协商任务——在还没有协商对象之前采用它，等于引入一个没有通信对端的协议。ACP 已经承载委派，包括委派给其他厂商的 agent，而 ACP 接缝已经建好。这件事保持开放：当客户确实需要够到一个 A2A agent 时，就是重新考虑的理由，而 subagent 接缝就是它该挂上来的地方。

### 组织可以自带供应方

平台默认提供模型，而组织也可以为该部署登记过的某个供应方提供自己的凭据。一个供应方族是 [`packages/llm`](../../../../packages/llm/README.zh.md) 里的一个包，拥有一家供应方的传输、认证与模型能力声明；凭据是租户配置，与其余租户配置一样按请求解析。

用 `DEEPSEEK_BASE_URL` 替换端点不是这件事。那是在进程层面给一个适配器改道，所以它服务的是"换了一个兼容端点的部署"，无法在同一个托管产品里服务分属不同供应方的两个组织。把每家供应方各自命名为一个包，才让第二个组织成为可能。

能力差异由供应方声明，不由 agent 去探知。上下文窗口、图像输入、提示词缓存行为、以及模型是否接受会话中途的工具更新，本来就来自目录；第二个族声明同样的事实，而循环继续从同一个地方读它们。

### 计量跟人走

用量归属到**行事的那位成员**，而不只归属到组织，这样组织才能看清自己哪些人、哪些部门花了多少。在平台提供模型的场合，这份归属同时用于执行：配额属于某个成员身份与某个计划，额度用尽则工作停止。

组织自带模型凭据时，用量只做记录以供查看，不执行任何限制。平台不持有那个账户，看不到它的余额，也不该假装存在一条它根本无法施加的限制。显示一条并不生效的配额，比什么都不显示更糟。

## Alternatives considered

**一个 agent 一个进程，子 agent 也算。** 这是"按 agent 隔离"的字面读法。否决：以父 agent 已完成轮次为起点的子 agent，正是本产品的委派模型，把每个子 agent 搬进独立进程，等于为最不需要协议的场合把一次直接调用换成一个协议。

**只用文件作用策略约束命令。** 它已经存在，不额外花成本。否决：它治理的是一个仍然保有宿主网络与内核的进程内部的文件作用。它是一条好策略，一条差边界。

**在共享存储里用查询条件区分组织。** 成本最低，也最常见。否决：它让每一条查询都成为一项安全控制，而第一条漏写条件的查询就是一次跨客户泄漏，其后再无任何屏障。

**一个 agent 一个容器。** 比一个团队一个容器更强。否决：它为了一条没人要求的边界而破坏进程内委派，毕竟团队是同一个客户授权的工作。

**现在就采用 A2A。** 多厂商 agent 互操作确实在往那边走。暂缓：目前没有对端，而 ACP 已覆盖委派，包括跨厂商的委派。

**替换端点，而不是新增供应方族。** `DEEPSEEK_BASE_URL` 本来就能给传输改道，而协议就是 Anthropic Messages API，所以接一家兼容供应方不花成本。作为托管的答案否决：它是进程层面的替换，服务的是一个部署，不是同时分属不同供应方的两个组织。对独立部署，它仍然是对的答案。

**只按组织计量。** 更简单，也与组织被计费的方式一致。否决：组织无法管理自己量不到的席位和部门，而按成员归属正是让席位有意义的那件事。

## Acceptance criteria

- 一个运行时恰好服务一个组织；它的会话根目录、存储与工作区不与另一个组织的运行时共享。
- 主 agent 与它创建的子 agent 跑在一个进程里，子 agent 仍如今天一样以父 agent 已完成的轮次为起点。
- 命令在容器内运行，容器的文件系统是会话工作区，网络可达范围是该组织允许的那些；文件作用策略在容器内部仍然生效。
- 跨进程的委派，包括委派给非 lyness agent，一律走 ACP；不引入新的 agent 间协议。
- 第二个供应方族作为独立的包存在，声明自己的传输、认证与模型能力，且 agent 循环从目录读取能力，而不是从某个供应方专用分支读取。
- 组织自带的模型凭据是按请求解析的租户配置，不是进程环境变量。
- 用量记录行事的成员身份，而不只记录组织。
- 使用平台提供的模型时，额度用尽即停止后续工作；使用组织自带凭据时，记录用量且不声称任何限制。

## Risks

**按组织分进程改变密度与成本。** 一个客户一个运行时是本设计中最主导的基础设施决定，它为每一种定价设下地板。小组织是难办的那一类。

**容器多出一层要运维。** 镜像生命周期、冷对话的启动时延、以及容器在命令执行中途消失时会发生什么，都是新的运维面。因容器消失而失败的命令，绝不能在 agent 看来像是命令本身失败了。

**进程内的团队是一个信任单位。** 团队内部没有边界，所以子 agent 与父 agent 同权。对客户主动要求的委派而言这是对的，它也意味着：说服父 agent 去委派的提示词，同时继承了父 agent 的触达范围。

**一家供应方的假设已经长在树里了。** `packages/llm` 里的一切都是针对一家供应方写的，而第一个第二族正是"其中哪些是协议事实、哪些只是那家的习惯"变得清楚的地方。`deepseek-llm-api-extensions` 这个包名已经点出了那一类不会通用的东西。

**无法执行的配额容易被误读。** 自带模型的客户会看到用量数字，并可能以为数字背后存在一条限制。界面必须明说它只报告、不限制，否则第一张意外账单就会被归到平台头上。
