# Agent Note: 模型是部署方的决定，而用户得到的是一份免费额度

Status: proposed

[English](2026-10-14-the-model-is-a-deployment-decision.md) | 中文

## Problem

今天，模型是谁站在产品前面谁说了算，而由此带来的三个后果，对本 harness 出厂的两种产品而言都是错的。

**一次部署可以在完全没有模型的情况下完成。** `dsh-base` 挂载了不带密钥的 DeepSeek 适配器，以及零条路由的 pi-ai 路由器，所以一次什么都没配的启动会成功、会把界面服务出去、并创建出根本无法回答的会话。失败在第一条提示词那里、在一个用户面前到达，而不是在造成它的那次部署那里。

**每个用户都能改写模型配置。** Models 页面会为任何打开它的人写入 provider 路由与凭据引用。对托管产品来说，这是用户在编辑运营方的成本基础；对企业私有部署来说，这是用户离开了他所在组织批准的那些模型。本该阻止它的那条限制被明确地缺席了：租户配置控制器记着「把保存限制给管理员，要等用户记录」，而本 harness 没有用户记录——`identity` 里只有一个匿名 id，别无其他。

**一个没有自己模型的托管用户，根本无从开始。** 产品今天的答案是那个索要 DeepSeek 密钥的引导弹窗——对一个在本地跑它的开发者而言这是对的答案，对一个为了使用服务而来的客户而言这是错的。树里任何地方都没有计量额度：`token-meter` 测量一次请求的代价，并明确写着它「不做任何循环决策」，而积分、余额、赠送、拒绝，一个都不存在。

已经存在的，是答案的形状。[`tenant-config`](../../../../packages/tenant/tenant-config/README.zh.md) 定义了一个租户在每种模态下可用的模型、首选的那个、到达它们的 provider 授权，以及它可用的特性——其中密钥以凭据引用而不是值的形式持有。它没有被任何出厂 bundle 挂载，而它唯一的两个使用方是一份目录清单和它自己的 RPC 面，所以其中一个字都没有被强制执行。

## Proposal

模型成为部署方的决定。用户得到的是「在部署允许的范围内选择」，而在托管部署上——当他什么都不自带时——还得到一份免费额度。

### 两种出厂形态是两份模板，不是一个开关

DeepSeek Harness 出厂两个产品，而它们的差别在于「哪些子系统存在」，不在于某一个子系统的行为如何。

**托管**形态服务许多组织：它有租户、计量积分，并由 DeepSeek Harness 运营。**独立部署**形态跑在某一个客户自己的服务器上、服务这个客户自己的员工：它没有租户、没有积分、也没有任何形式的支付，因为这个客户买的是系统本身，不是对它的使用量。

这个差别是一份 profile 模板，不是一个运行时模式。`PROFILE_TEMPLATES` 本来就按形态给出一串 bundle 清单，于是托管模板选中租户与积分这两个模块，而独立部署模板根本不选它们。因此积分在独立部署里是**不存在**，而不是被关掉——这是「没有额度」唯一不会把余额泄漏进某个界面、某条日志、或某条报错的版本。

另一个方案是运行时的 `mode: hosted | enterprise` 标志，而它更差，差在本仓已经懂的那个地方：每个使用方都多出一条分支、每条分支都是错误形态可能出现的地方，而那个标志必须在每处都被正确查询。一个没有被挂载的 bundle，没有任何分支可供弄错。

### 部署声明自己的模型，没声明就启动失败

一次部署在服务任何东西之前，先声明它服务哪些模型。一个什么都没声明的组合会在加载时失败，并以此作为原因，而不是先启动起来、再按会话逐个失败。

这就是已有的 `tenant-config` 名册，是被挂载起来而不是被重新发明：每种模态的 `models.available`、作为默认值的 `models.preferred`，以及每个 provider 一条携带凭据引用的 `ProviderGrant`。声明它，才算完成一次部署。

失败属于加载时，因为那里它是自包含的，而且运营方在场。一次会话时的失败，到达的是一个无力修它的用户。

### 允许集合在「选择模型的那个地方」被强制执行

强制执行住在「为一次请求解析路由」的那个操作里，而不是在展示选项的那个界面里。一个过滤列表的界面是展示；一个拒绝未列出模型的解析器才是规则。别的做法都会被下一个调用方绕过——一次 RPC、一个 preset、一份 profile 补丁。

一次指名了租户 `available` 集合之外的模型的请求会被拒绝，并以此为原因。一次什么都没指名的请求取 `preferred`。

### 模型配置对用户是只读的，而界面会说明这一点

在部署方拥有该配置的地方，Models 页面变为只读，并说明是哪一方拥有它。`tenant-config` 已经携带了界面所需的那个事实：后端声明自己能否被保存，于是页面显示或隐藏保存，而不是靠失败去发现。

只读不等于隐藏。用户仍然看得到自己可以用哪些模型、哪个是默认，并且仍然按会话在其中挑选；他不能做的是添加 provider、改端点、或写入凭据。

「拥有它的那一方是谁」按形态不同。在托管形态上，DeepSeek Harness 自己的运维设定对每个租户与每个直连用户都生效的默认值，而租户的管理员可以为本租户改它；一般用户只是使用。在独立部署形态上，客户的管理员在管理界面里设定那份列表，而被授权的用户在其中挑选，无法改动它。

两种形态都不允许一般用户添加 provider、改端点、或写入凭据。这是两种形态共有的唯一一条规则，也正是解析器所强制执行的那条。

单租户的开发者安装保持今天的行为，因为一个不挂载任何租户后端的部署，它自己就是运营方。那是已有的单租户规则，不是一条新例外。

### 没有自己模型的托管用户，每天得到一份积分额度

本节只描述托管形态。独立部署不挂载积分模块，所以这里的一切在那里都不存在。

单位是**积分**（英文 credits）。托管部署每天向每个用户赠送 **500 积分**，按 **UTC+8** 计算「每日」，由模型请求消耗，余额归零时拒绝服务。赠送量与按用户上限都可以改动——由 DeepSeek Harness 运维为整个部署改，由租户管理员为本租户的用户改——所以 500 是一个经校验的默认值，不是常量。

这份额度是一份带流水的余额，不是一个计数器。一次客户无法对账的拒绝是一个工单；而一份「每一笔扣减都点名造成它的那个会话」的余额是可以回答的。这与推导记忆那份笔记对「失效」所用的推理相同：那份记录本身就是产品，不是实现细节。

消耗由已有的 `token-meter` 测量——它已经能从会话日志确定性地给一次请求定价，并且不做任何循环决策。计量保持为测量；额度拥有「拒绝」这个决定。

### 耗尽会停下这一回合、说明原因、并挡住下一回合

一个把余额用尽的回合会停下来，而不是透支。它说明为什么，它不再开始下一个，并指向充值路径。已经做完的那部分工作留在会话里，因为丢掉它等于丢掉积分已经买到的东西。

选择「停下」而不是「做完并透支」，是因为透支是运营方没有同意过的成本，也因为一个能超出余额的用户等于没有余额。所以这个停止在「发出请求」的地方强制执行，而不是在某个界面里宣告。

### 积分按用户计，而租户为自己的用户设上限

余额属于用户，因为赠送是按登录到达的。租户另外为自己每个用户设置可用额度，于是组织自己控制自己的消耗，而不必由 DeepSeek Harness 代它去给成员设一个上限。

于是有两个权威在约束同一份余额：部署方的赠送策略，以及租户的按用户上限。两者中更低的那个生效，而拒绝会点名撞上了哪一个——一个只被告知「积分不足」的用户，分不清自己该等明天，还是该去找他的管理员。

### 钱由谁收，是一条边界，不是一个设置项

租户的用户把钱充进**租户自己的对公银行账户**。DeepSeek Harness 只向租户收取平台使用费，别无其他。因此需要一个管理界面来维护租户的对公账户信息，因为租户才是它自己用户付钱的对象。

不属于任何租户的用户，是 DeepSeek Harness 服务的普通用户，遵循 DeepSeek Harness 自己的规则，包括它自己的充值路径。

这是一条责任边界，而不是一个配置选择，并且它决定了本 harness 绝不能做的事：对租户的用户而言，DeepSeek Harness 不持有资金、不做结算、不是记录商户。流水记录的是积分，那是一种服务单位；钱在租户与它自己的用户之间流动，走的是一条 DeepSeek Harness 只提供账户信息、而不站在其中的路径。

由此可知，这两类人群不能共用同一套充值实现。租户用户的购买是租户的交易；直连用户的购买是 DeepSeek Harness 的交易。积分流水是共用的；支付路径不是——而一个把两者合并的设计，会在无意间让 DeepSeek Harness 成为每一个租户的支付处理方。

### 引导不再追问部署方已经决定过的事

首次运行的那个凭据弹窗其实已经自己解决了：当任何一个 provider 可用时，`onboardingReadiness` 报告 `provider-ready`，而那个弹窗什么都不渲染。一个声明了自己模型的部署满足该条件，所以这一半不需要任何改动。

那条内测声明被取消，而不是改成有条件的。它是一段关于「预发布构建」、面向它的开发者的陈述，而本产品的任何形态都不该以它开场：托管客户不是来读它的，而独立部署的用户用的是他自己实施方部署的那个构建。

它原本承载的东西——这是一个早期构建，以及改了什么——移到一条**系统公告**里，由用户在想看的时候打开，里面放更新日志与正在运行的版本。一条会打断人的通知，是一个会等人的页面的更差版本。

## Alternatives considered

**把模型留给用户，并在文档里写明运营方不该暴露 Models 页面。** 不需要改代码。否决：一条写在文档里的惯例不是权威边界，而无论界面显示什么，那个页面都能通过 RPC 到达。

**在 Models 页面与模型选择器里强制执行允许集合。** 用户永远看不到自己不能用的模型，这是用最少的工作拿到大部分价值。作为「足够」被否决：一个 preset 行、一份 profile 补丁、一次直接 RPC，各自都能在不经过任何界面的情况下到达解析器——而这正是本仓自己那条「决定在做出它的那个操作里强制执行」的规则。

**用钱而不是产品单位来计量。** 以货币计的余额在购买时不需要换算。作为主单位被否决：一次请求的价格取决于某个 provider 的费率，而运营方可能改动它、也可能不愿按次披露它；而一个拿余额去对照任务的用户，无法用一个会动的单位来推理。一个由 token 定价的产品单位，让用户看到的东西保持稳定，而运营方的成本在底下变化。

**按会话而不是按天赠送额度。** 更简单，而且不需要时钟。否决：它奖励「多开会话」，与意图中的形状正好相反，而且让重度用户与轻度用户拿到同样的总量。

**让托管用户自由配置自己的模型。** 这对运营方零成本，并且消掉了额度这个问题。作为默认被否决：一个用户的密钥进入运营方的进程，是运营方的责任，而决定是否接受它的那一方是部署方。在部署方允许的地方，它仍然可用。

## Still to settle

上面那些决定已经把形状定下来了。还剩两个值，而它们都不阻塞开工。

**平台使用费自身的形状。** DeepSeek Harness 向租户收什么，是一个商业决定，本笔记只在一点上约束它：它向租户收取，绝不向租户的用户收取。

## Acceptance criteria

- 一个没有声明任何模型的组合在加载时失败，并点名这一缺失作为原因。
- 一次指名了租户可用集合之外模型的请求在路由解析器里被拒绝，而一次什么都没指名的请求解析到 `preferred`。
- 对一次不经过任何界面就到达解析器的请求，该拒绝同样成立，并且是通过解析器而不是界面被证明的。
- 在部署方拥有配置的地方，Models 页面是只读的、会说明是哪一方拥有它、并且仍然显示用户可用的那些模型。
- 一个不挂载任何租户后端的部署，其单租户行为保持不变。
- 托管用户的积分扣减点名花掉它们的那个会话，而一份耗尽的余额以用户可以据此行动的理由拒绝。
- 一个把余额用尽的回合在不透支的前提下停下，保留已经做完的工作，并且不再发起任何请求。
- 拒绝会点名撞上的是部署方的赠送额度、还是租户的按用户上限。
- 租户的对公账户信息经由一个管理界面维护，并且没有任何代码路径让 DeepSeek Harness 成为租户用户充值的收款方。
- 内测声明弹窗已不存在，而更新日志与正在运行的版本可以从一条由用户自己打开的系统公告到达。
- 独立部署模板不选中任何积分模块，并且在独立部署上不存在可到达的余额、赠送、流水或充值文案。
- 在托管形态上，每日赠送默认 500 积分、按 UTC+8 计算，且赠送量与租户的按用户上限分别可由各自的权威改动。
- 两种形态上的一般用户都不能添加 provider、改端点、或写入凭据，并且这是通过解析器与保存路径、而不是通过界面被证明的。

## Risks

**解析器里的强制执行会触达每一个调用方，包括那些本该绕过它的。** 部署方自己的运维任务、测试里的一次 replay、一个被播种的会话，全都要解析路由。一条没有权威豁免就写下的规则，会拒绝运营方本来想要的工作；而一条写得过松的豁免，就是这条规则存在所要防的那个绕过。

**额度让「拒绝」成为一次模型请求的正常结果之一。** 每一个「请求要么成功、要么技术性失败」的界面，都因此多出第三种既非成功也非失败的情形，而压缩、重试、排队这几条路径各自都要决定如何处置它。漏掉一个，就会留给用户一个既没完成、也不解释自己的回合。

**对单租户用户而言，一个只读的 Models 页面比没有 Models 页面更糟。** 开发者安装保留写权限，于是两种模式分叉，而权威检查里的一个 bug 最可能的表现形式，就是一个开发者无法配置自己的模型。

**积分流水是一份按用户的使用记录。** 它比记忆敏感度低，但仍然描述了一个具名的人在什么时候做了什么，而持有它的托管部署会一并继承随之而来的保留期问题。

**独立部署不能露出任何积分痕迹，而痕迹藏在共用代码里。** 即使模块没有被挂载，locale 词典、错误词汇、会话事件这些东西仍然在两种形态之间共用。一条住在共用词典里的「积分耗尽」文案，或者一条共用类型能表达的拒绝原因，会到达一个既没有余额、也无法据此行动的独立部署用户。让模块不被挂载是必要的，但不充分；它的词汇必须跟它一起走。

**两条支付路径会诱使人把它们做成一套实现。** 流水是共用的，充值按钮看起来也一样，所以最省事的下一次改动永远是：把租户用户的支付走上与直连用户相同的那段代码。仅这一次改动，就会让 DeepSeek Harness 成为每一个租户的用户的记录商户——而这正是本笔记唯一禁止的结果。那条分隔需要在代码里看得见，而不只是写在本文件里。

**租户上限与部署赠送可以无声地彼此不一致。** 两个权威约束同一份余额，意味着一个用户可能被他的管理员并未设置的限制挡住，也可能越过管理员以为自己已经设置的那个限制继续工作。在拒绝里点名「生效的是哪一个限制」，正是让这件事可排查的东西；省掉它，就会产生双方都无法解决的工单。
