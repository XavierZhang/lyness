# Agent Note: 模块 bundle 如何往不属于自己的 preset 里加一个工具

Status: proposed

[English](2026-10-10-preset-row-contributions.md) | 中文

## Problem

[每个默认模块各自是一个出厂 bundle](2026-10-08-default-modules-and-views.zh.md)，正是这一点让平台拥有"单独升级一个模块而不必发布整个产品"的通路。而其中一半的模块无法这样打包。

贡献面向模型的工具的模块，它的行在某个 agent preset 内部。一个 preset 是一个 `@lyness/lyn-agent-preset` 行，它的 `config.plugins` 持有整份清单，而[补丁替换目标行的整个 `config`](../../../../packages/bundle/web-app/README.zh.md)。所以另一个 bundle 想给 `work` 加一个工具，就得把 `work` 已有的每一行重述一遍。这不是打包，是复制；而这份复制会在 preset 第一次变动时过期。

这个劈分很干净，也很没用。agent 终端、语言服务器、计算机操作、浏览器操作、轮次交付物、运行时自修改，以及持久记忆的写入工具，全都在 preset 面上。其余模块在宿主面，今天就能打成 bundle。十二个里有六个被一个不存在的机制挡住。

显而易见的绕法会让事情更糟。把模块的工具留在 profile bundle 里、而它的服务单独出厂，意味着客户选中的单位不再是那个模块：关掉模块之后，它的工具仍然注册着，而它们的服务已经不在了。

## Proposal

模块 bundle 往 preset 里**贡献**行，由 preset 注册表合并它们。

### 贡献指明的是目标类别，不是 preset id

贡献声明自己加入哪些 preset，按**类别**——服务于人的那些 preset——而不是列出 id。模块不应当需要知道存在哪些视图默认，而新增一个 preset 的部署也不应当需要去改每一个模块。

官方四种模式所用的那四个 preset id 不接收任何贡献。它们按上游出厂的样子保留——这是[preset 那部分工作](2026-10-08-default-modules-and-views.zh.md)在它们旁边新增 `work` 与 `build` 时做出的承诺；想够到它们的模块要的是另一个 preset，不是一次贡献。

### 位置来自中央分配

被贡献的行在工具顺序里的位置由中央分配，正如 [`lyn-system-prompt`](../../../../packages/core/system-prompt/README.zh.md) 已经在分配提示词段与运行时上下文的位置那样。到达顺序不得决定它：工具目录的顺序是请求前缀的一部分，所以开着同样模块的两个部署必须产出同样的目录、同样的顺序，否则相同配置会产出不同的缓存。

### 重复 id 在挂载时失败

两次贡献争夺同一个行 id 是一个组合错误，不是"后写者胜"的合并。它在 preset 挂载时失败——那是两者都已知的最早时点——而失败要点明两个贡献者。

### 迟到的贡献让那一代退休，而不是去打补丁

启动顺序把贡献排在 preset 之后。模块 bundle 在有序 bundle 列表里位于声明 preset 的那个界面 bundle 之后，所以等到某个模块来贡献时，它要加入的那个 preset 早已激活并挂好了一代。一个要求"贡献必须先到"的机制会在每一次启动时失败。

所以一次贡献注册会让每个接收贡献的 preset 的当前那一代**退休**，并激活新的一代。已经绑定到退休那一代的 agent 保留它直到自己结束——注册表既有的保留计数会托住它，最后一个离开时被回收——而下一个 agent 拿到的是包含该贡献的那一代。这与一个定义自己被撤回时已经走的路是同一条，不是第二条。

值得写明的后果：会话中途打开一个模块不会改变正在运行的 agent，它改变的是下一个。别的做法都意味着去重写一个已经在途的请求的工具目录。

### 贡献是一个 effect

关掉模块 bundle 就撤回它的行，因为贡献和其他每一项注册一样经 `ctx.effect()` 注册。没有第二条移除路径，也没有任何状态能活过拥有它的那个模块。

### 宿主面与 preset 面保持区分

一个模块 bundle 可以两者都带：宿主行在它自己的补丁层里，preset 行作为贡献。它不可以做的是：注册一个工具，而它并没有同时挂载那个工具的服务——客户会看到的失败是"一个存在却无法工作的工具"，而挂载正是这一对可被检查的地方。

## Alternatives considered

**在 Loader 里按行 id 合并 `config.plugins`。** 表面上改动最小：补丁合并数组而不是替换数组。否决："补丁替换目标行的整个 `config`"这条在整棵树里被依赖，为了让一个字段特殊而改掉它，会改变每一个既有补丁层的解析方式。

**一个模块出厂一个 preset。** 那就没有东西需要合并，因为每个模块拥有自己的 preset。否决：preset 是人去选的模式，不是模块清单，而十二个模块会变成十二个没人要的模式。

**把每个工具行都留在 profile bundle 里。** 完全不需要新机制，而模块的服务仍然单独出厂。否决：客户选中的单位不再是模块，而关掉其中一个会让它的工具注册着一个已经缺席的服务。

**让贡献指明 preset id。** 更显式，而且模块可以只针对某一个模式。否决：那样每个模块都要带一份清单，而部署新增 preset 时这份清单就过期；而且没有任何东西能阻止模块伸进那四个被保留的官方模式。

**按 bundle 的选中顺序给贡献排序。** 不需要中央分配，而有序的 bundle 列表本来就存在。否决：工具目录的顺序是请求前缀的一部分，所以开着同样模块、但选中顺序不同的两个部署，会为相同配置产出不同的缓存。

## Acceptance criteria

- 模块 bundle 能往服务于人的 preset 里加一个工具行，而不重述任何不属于它的行。
- 官方四种模式所用的那四个 preset id 不接收任何被贡献的行。
- 被贡献的行的位置来自中央分配，且开着同样模块的两个部署产出逐字节相同的工具目录。
- 两次贡献争夺同一个行 id 时在 preset 挂载时失败，且失败点明两个贡献者。
- 关掉一个模块 bundle 会移除它贡献的行，且没有第二条移除路径。
- 在某个接收贡献的 preset 已经挂载之后注册的贡献，会让那个 preset 的当前一代退休并激活新的一代；已经绑定到退休那一代的 agent 保留它直到自己结束。
- 贡献的工具其服务不由同一个 bundle 挂载时，在挂载处被拒绝，而不是产出一个无法工作的工具。

## Risks

**preset 的组合不再能从一个文件读完。** 今天 `work.patch.yml` 展示 `work` 拥有的一切。有了贡献之后，读它不再够：读者还需要那份被选中的模块 bundle 列表。开发视图正是"解析后的组合必须可读"的地方，而在它可读之前，这是用一种清晰度换取打包方式。

**切换一个模块会改变请求前缀。** 贡献一个工具会改变目录，所以打开一个模块会让该 profile 上每个会话的缓存前缀失效。这是对的、也不可避免；值得写明是因为模块开关从此有了"只在宿主面开关"所没有的代价。

**快照预期多出一个依赖。** 每个 preset 快照的工具目录从此是"哪些模块 bundle 被选中"的函数，所以钉住目录的快照也钉住了那份选择。那份被钉住的选择必须在场景里可见，而不是由默认 profile 隐含。

**每次贡献都让一代退休，使启动期重复做这件事。** 启动期每个贡献的模块都会让接收贡献的 preset 退休并重建，所以有六个贡献模块的部署会在第一个 agent 出现之前重建它们六次。这是对的，也是浪费的；要不要加一个结算点，是第一个真正感到它的部署该回答的问题，而不是现在就加的理由。

**中央分配是刻意设置的瓶颈。** 每个贡献工具的模块都需要在一个地方分配位置，所以并行开发的两个模块会碰同一张表。这与提示词段分配已经在付的代价相同，接受的理由也相同。
