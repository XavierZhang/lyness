# Agent Note: 会话归属于打开它的那个人

Status: proposed

[English](2026-10-07-session-ownership.md) | 中文

## Problem

会话是一个人与 agent 之间的持久对话。它身上没有任何东西记录这是谁的对话。

最接近的记录是 [`lyn-tenant-session`](../../../../packages/tenant/tenant-session/README.zh.md) 在创建时写入的 `tenant/identity` 事件，而它记的是**本部署被配置的**租户，不是发起该请求所解析出的租户。在私有部署里两者是同一个，所以缺口看不见。在托管产品里一个进程服务许多组织，它存下的每个会话都会带着同一个租户——归属记录对除一个客户之外的所有人都是错的，而会话日志是持久的，于是这个错会永远留在那里。

组织之下根本没有身份。[`lyn-tenant-request`](../../../../packages/tenant/tenant-request/README.zh.md) 把一次调用解析到一个组织，而不是组织里的某个人；整棵树里唯一像"用户"的东西是 [`anonymous-user-id`](../../../../packages/identity/anonymous-user-id/README.zh.md)，而它存在的目的恰恰是在**不识别任何人**的前提下关联遥测。所以"谁打开了这个对话"这个问题，眼下还没有可记录的答案。

有两件事让它紧迫而不只是不完整。会话日志是已发布数据：已提交的世代永不重写，因此记错的归属会一直错下去，而分两步补齐归属要付两次格式变更而不是一次。另外，一个说不出"是我们的哪个人打开了这个对话"的组织，无法为它负责——而这恰恰是企业客户对一个代其运行 agent 的平台提出的第一个要求。

## Proposal

会话归属于打开它的那个人。组织对它的主张经由这个人持有，并按对话开始时的状态记录下来。

### 会话记录什么，记一次

创建时，会话携带一条持久的归属事件，指明两件事：

- **所有者**——打开它的人，在托管产品里始终存在；
- **他当时以哪重成员身份行事**——当时占着哪个组织的席位；以自己的身份行事时没有。

一个人只有一个身份，却可以同时持有多重成员身份——他自己的，以及他所属的每个组织各一个——因此"哪个组织"不是这个人的属性，而是这次行为的属性。一个人以 Acme 的身份打开的对话就是 Acme 的对话，无论他还是谁的成员；而且对话不跨成员身份：为 Acme 打开的那些，不在他以 Globex 身份或以自己的身份所看到的之中。

成员身份是被记录下来的而不是推导出来的，因为它的两端都会动。一个从 Acme 离职加入 Globex 的人，不能把三个月的 Acme 对话一并拖进 Globex 的账下；而一个组织在读自己的历史时，应当看到每个对话发生当时的事实。所有者回答"这是谁的"，被记录的成员身份回答"它是在谁的屋檐下打开的"。

该事件在创建时写入一次，永不重写。它就是归属的权威记录。

### 个人没有组织

不属于任何组织的客户直接拥有自己的会话，归属事件里不记租户。这个**缺席本身**就是个人这一情形，没有任何东西代替它。这样系统里的每个组织都是真实的组织——[租户级品牌](2026-10-07-per-tenant-brand.zh.md)里的计划门禁，以及其他一切按组织计价的东西，都依赖这一点。

### 移除成员是归档，不是删除

组织可以结束一位成员的身份——移除此人，或回收他占用的席位。两者都不触碰会话记录：对话留下，归属与此前完全一致。

改变的是这个人的状态，而所有者已不在组织中的会话读作**已归档**。该状态由所有者推导而来，而不是盖在每个会话上，因此结束一段成员关系是一次写入，而不是扫过此人打开过的每一个对话；恢复一个被回收的席位也不需要第二次扫描来撤销。归档意味着**保留且组织可读**，而不是对组织隐藏：一个读不到自己需要为之负责的内容的组织，从归档里什么也没得到。

### 请求必须携带这个人，以及他所行事的成员身份

在一次调用能解析到"以某重已知成员身份行事的人"、而不只是一个组织之前，上面这些都无从记录。一次调用如何说明它以哪重成员身份行事——靠它到达的地址，还是靠客户端携带的一个上下文——是下面那一层的待决问题；本笔记只要求这个答案在请求里是**明示的**，而不是从此人的成员关系推断出来的，因为一个持有两重成员身份的人会让推断变成猜测。那一层——用户、他们在组织中的成员关系、各自能做什么——是前置条件，本笔记不设计它。

关于它的一个决定已经作出，并且因为上述操作依赖它而记在这里：组织完成入驻后，由**平台管理员为其指派第一位租户管理员**，此后组织才能自行配置与管理，包括移除成员。组织不能自举出自己的第一位管理员。设计用户与角色层的那份笔记拥有这条规则；记在这里是为了让归档与回收操作有一个确定的执行者。

### 次序

归属与组织一起、作为**一次**格式变更进入会话日志，时间在用户层存在之后。现在先记组织、以后再记人，会让已发布的会话数据变更两次，而第一个世代会是一个谁也不想要的形状。

## Alternatives considered

**把归属继续放在 `tenant/identity` 里。** 该事件已经记了一个租户，顺带记上人即可。否决：它的存在是为了记录组织向模型请求贡献了什么——它的 constraints 与 personality，逐字记录——那是另一个事实，有另一种生命周期。归属拿到自己的事件，`tenant/identity` 只保留它本来要做的那一半。

**现在先记请求的组织，以后再补人。** 能更早修掉当下的缺陷。否决：它要对已发布的会话数据改两次，而中间那个世代记录的是"有组织、没有所有者"，这是任何消费者都不想要的形状。

**给每个个人配一个个人组织。** 统一：每个会话都有租户，每次查询只有一种形状。否决：它会让系统里充满只有一个成员、没有管理员的组织，并使每一个按组织作出的决定——计划门禁、品牌、计费——都在回答一个关于虚构之物的问题。

**从所有者的成员关系推导组织。** 不必加第二个字段，成员关系本来就存着。否决有两重：一个人可以同时持有多重成员身份，于是根本无从推导；即便只有一重，人一换组织它就改写了历史——而这恰恰是归属的权威记录绝不能做的事。

**删除被移除成员的会话。** 干净，而且大概也是离职者的预期。否决：组织仍要为在其屋檐下发生的事负责，而删除已发布的会话数据在本产品的其他任何路径上也不提供。

**成员被移除时在每个会话上盖 `archived`。** 直接，查询只读一个字段。否决：移除时每个对话写一次、恢复时再写一次，并且它制造了第二个事实来源，可能与它所依据的成员关系互相矛盾。

## Acceptance criteria

- 以某重成员身份行事的人创建的会话，记录此人为所有者，并记录该成员身份对应的组织；以自己的身份行事的人创建的会话记录所有者、不记组织。
- 在一重成员身份下打开的会话，不出现在此人以另一重成员身份、或以自己的身份所看到的会话之中。
- 所有者此后加入、离开或在组织间流动时，已记录的成员身份不变。
- 结束一位成员的身份不改动任何会话记录，而该成员拥有的每个会话读作已归档；恢复其身份使它们回到活跃状态，同样不触碰那些记录。
- 组织能读到被移除成员的已归档会话。
- 不带归属事件的会话——本次变更之前写入的每一个——读作"无归属"，且任何消费者都不从"后来是谁打开了它"去推断所有者。
- 托管产品拒绝为一次没有解析出人的调用创建会话。

## Risks

**格式变更收不回来。** 已发布的会话数据允许一个以版本命名的后继世代，但绝不允许重写，因此归属事件的形状必须一次定对。该事件携带 id 而不是名字：人的显示名与组织的显示名都会变，两者都不该出现在一条永不重写的记录里。

**由成员关系推导的归档可能与人们的预期不符。** 管理员移除一位成员后，会立刻看到他的对话变为已归档，包括正在进行中的对话。进行中的对话应当被中止还是允许完成，需要它自己的答案；本笔记不提供。

**前置条件很大。** 用户、成员关系与角色是比本次变更更大的一摊工作，而本次变更不能先于它们上线。在用户层还在变动时就把会话格式当作可以定稿，会冻结一个用户层也许还想调整的身份形状。

**无归属的历史会一直无归属。** 本次变更之前写入的每个会话都没有所有者，之后没有任何流程能诚实地补上一个。消费者必须把这个缺席显示出来而不是去猜，这意味着托管产品的第一份归属报表从本次变更开始，而不是从最初开始。
