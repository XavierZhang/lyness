# Agent Note: 一个属于个人的平面，以及什么是这个人自己的

Status: proposed

[English](2026-10-28-the-personal-plane.md) | 中文

## Problem

设置是一张清单，而它把两个不同的问题混在一起。`general`、`models`、`credits` 和 `plugins` 问的是「这个读者用什么工作」；`people`、`bots`、`sign-in-channels` 和 `history` 问的是「一个组织或这套部署维护什么」。一个普通成员打开设置会被提供全部这些，并在其中四个里读到一条拒绝提示，而那四个区块各自的 README 都记着同一条限制：这个区块对每一个读者都提供，因为导航在区块自己的读答出来之前不知道调用方的身份。

这种混在一起还藏着第二个缺口。有三样一个人有权知道的东西，根本没有地方可去。

他自己的限额是第一样。到这一周之前，一个账户只答余额、别无其他，于是一个人分不清「今天用得少」和「额度被调低了」；现在余额带着生效的额度、它所在的周期、这个周期什么时候开始、以及到现在花掉了多少，而积分页把它展示给每一个读者。那是其余部分该跟上的模式，不是一个例外。

他自己的指令是第二样。记录在案的提示词分层是平台、组织、用户、agent，其中三层现在都有了：部署的性格、从会话自己的记录合成出来的租户身份、以及 agent 自己的性格或一个 bot 的。用户那一层从来没有一份记录可以承载它。`lyn-agent-instructions` 从磁盘读 `AGENTS.md`，这对一个坐在自己机器前的人是正确答案，对一个用浏览器连到托管部署的人完全不是答案。

关于他被记住了什么是第三样。`lyn-memory` 本来就把 `member` 和 `shared` 两种范围分开，所以一个人要求记住的那些事实，和一个工作区共享的那些是可区分的——而没有东西向一个人展示其中任何一组，也没有东西让他删掉某一条。

## Proposal

把设置拆成两个平面，并让个人平面成为一个人读取和修改属于他自己的东西的地方。

**两个平面，一次读。** `identity.viewer()` 本来就答出调用方的身份，带着它的角色和组织。把那次读从 `ui-sign-in` 自己的 store 提升成一个任何界面都可以读的客户端服务，并让设置导航按平面给区块分组：个人平面始终显示，管理平面只对角色不是 `member` 的身份显示。由一次读决定它，于是导航和账户那一行共享同一个答案，而不是各问一次。

**个人平面只提供这个人改得了的东西，并把他改不了的那些说出来。** 这正是把这份设计和「照抄一份竞品设置清单」分开的那个取舍。在一个模型、preset、skill、插件和 MCP 服务器都由部署组合出来的产品里，ChatGPT、Claude 和 Cursor 放在个人设置底下的大部分东西，在这里都不是这个人该设的。一个提供了那些控件的平面，等于承诺下一次调用会拒绝的事，而这正是本仓库已经逐个区块禁止的做法。所以每一个条目要么带着一个这个人拥有的控件，要么读作「你可以用什么、以及是谁决定的」。

### 每个概念落在哪里，以及谁决定

| 竞品提供的概念 | 这里的平面 | 谁决定 | 今天的状态 |
|---|---|---|---|
| 名字、登录身份、所处身份、登出 | 个人 | 目录；登出是这个人的 | `identity.viewer()` 已答出；只有侧栏那一行展示它 |
| 用量、限额、重置、余量 | 个人 | 限额由管理员设 | 已交付 |
| 组织的预算与花费 | 管理 | 平台设，组织读 | 已交付 |
| 自定义指令、规则、「怎么称呼我」 | 个人 | 这个人 | **缺失**：提示词的用户那一层没有记录 |
| 记忆：关于我被记住了什么 | 个人 | 这个人和他的那些 agent | 以 `member` 范围存着；没有界面 |
| 外观、字号、语言 | 个人 | 这个人 | 已交付，在 `general` 里 |
| 快捷键 | 个人 | 这个人 | 已交付，在 `general` 里 |
| 连接与 MCP 服务器 | 管理，在个人里只读 | 部署把它们组合出来 | `mcp-client` 在组合里按条目配置 |
| Skill | 在个人里只读 | 这个人的 agent 所运行的那个 preset | `ui-skill` 负责调用它们；没有东西列出一个人可以用哪些 |
| 插件与扩展 | 管理，在个人里只读 | 部署 | 插件页已经存在 |
| 模型 | 管理，在个人里只读 | 部署和租户的模型清单 | 模型页已经存在 |
| Agent preset | 管理 | 部署 | 已交付 |
| 数据：导出、删除我的对话 | 个人 | 这个人 | `session-query` 能导出；没有个人界面 |

那张表里只有两行是设计本身，其余都是归位。**指令**需要一份记录，因为一个托管场景下的人没有文件。**记忆**需要一个界面，因为记录本来就有。

**用户那一层的合成方式和组织那一层一样。** 一条个人指令为这个人存着，在一场会话创建时写进那场会话自己的日志，并从日志而不是从存着的那条记录合成进提示词——理由和租户身份一样：一个人修改自己的指令，不能改变一场正在跑的对话已经说过什么；而任何到达模型请求的东西，都必须能从会话日志重建。那个区块的顺序排在组织的和 agent 的之间，这正是记录在案的分层里「没有更低的一层能移除更高的一层」的意思。

**一个只读条目说出是谁决定的。** 「你可以用什么」列出这个读者的 agent 实际拥有的那些 skill、工具、连接和模型，每一项都点名是哪个 preset 或者是部署给的。它是对「那些页面今天都用一条拒绝提示回答的那个问题」的一个回答，而且不花任何新的权限。

## Alternatives considered

**保留一张平清单，让每个区块各自汇报自己的拒绝。** 这就是今天。它让一个成员撞上四个死胡同，而那个修法得按区块写四遍而不是一遍；已经有四个 README 带着这条限制，这正是「形状不对，而不是那些区块不对」的证据。

**给个人平面自己一条路由，而不是设置里的一个平面。** 外壳、那些 slot 种类、locale 命名空间和 store 机制全都是为区块准备好的，而第二条路由会把它们复制一遍，换不来读者能说出名字的任何行为。等个人平面长出一个不是设置页的界面时，值得重新考虑。

**照抄一份竞品的区块清单。** 之所以否掉，是因为组合模型不同，不是因为那些清单不好。一个页面给一个人提供他自己的 MCP 服务器清单，而服务器来自组合——那就是一个产品会拒绝的控件；而本仓库自己的规则是：界面从「填充它的那个答案」里渲染它的控件。

**让指令像 `AGENTS.md` 那样是一个文件。** 这保住了一套机制，而且把桌面形态服务得很好。它完全没有服务托管形态：没有一个浏览器可以编辑的用户级全局文件，而三种产品形态每一种都要么被服务、要么被点名。一份存下来的记录服务全部三种，而那条文件链对一个工作区仍然是它本来的样子。

## Acceptance criteria

- 设置导航只对角色不是 `member` 的身份显示管理平面，由一次「账户那一行也共享」的 viewer 读决定。
- 一个成员打开设置，到不了任何一个「它自己的读会答出拒绝」的区块。
- 一个人读取并编辑他自己的指令，而之后创建的一场会话在它自己的日志里带着这些指令，并把它们合成进提示词、排在组织那一层和 agent 那一层之间。
- 一个人读取为他记录的那些 `member` 范围的记忆，并删掉其中一条。
- 一个人读取他的 agent 可以用什么——skill、工具、连接、模型——每一项都点名是什么给的。
- 每一个个人条目要么带着一个这个人拥有的控件，要么说出它所汇报的东西是谁决定的。

## Risks

**平面拆分是一个可见性决定，而一次读错身份会藏错东西。** 藏起管理平面是导航，不是权限：每一个管理调用都保留自己的检查，所以一次答错的 viewer 读只会多显示或少显示一个页面，不会授予任何东西。这正是要守住的性质——这次拆分绝不能变成「一个成员和一次管理操作之间唯一挡着的东西」。

**一条个人指令是一个人写的、会到达他自己的模型请求的文字。** 它追加在部署的和组织的那些区块之后，理由和租户的一样，所以它放宽不了一个 agent 能做的事；而它被记进会话日志，所以到达模型的是什么，事后读得出来。一套想禁掉它的部署，需要的是一个它可以不选的组合行，而不是这个平面里的一个开关。

**「你可以用什么」会长成关于能力的第二个答案。** 它必须在被问到的那一刻投影 agent 所读的那些注册表，而不是自己留一份清单——否则它就变成一个和 agent 实际拥有的东西不一致的页面。
