# Agent Note: 客户默认拿到哪些模块，以及看它们的两个视图

Status: proposed

[English](2026-10-08-default-modules-and-views.md) | 中文

## Problem

"一切皆是插件"是正确的原则，也是糟糕的默认值。它说清了运行时由什么构成，却没说清一个注册进来的客户实际拿到了什么；而在这棵树里，答案是"比已经建好的少"。

有些能力已经存在、已有测试，却没有任何出厂 profile 挂载它们。[`tool-lsp`](../../../../packages/lsp/README.zh.md)、[`computer-use`](../../../../packages/computer-use/README.zh.md)、[`browser-use`](../../../../packages/browser-use/README.zh.md)、[`hooks-claude-code` 与 `hooks-codex`](../../../../packages/hooks/README.zh.md)，以及面向 agent 的 [`tool-terminal`](../../../../packages/terminal/README.zh.md)，只出现在快照组合里。[`webhook`](../../../../packages/webhook/README.zh.md) 只出现在一个 CLI 示例和一个测试 fixture 里。另一些只挂在恰好一个 profile 上：`schedule` 和 [`workspace-changes`](../../../../packages/deliverables/README.zh.md) 在 `web-app`，而 [`tool-cordis`](../../../../packages/extensions/README.zh.md) 只在创造模式预设内部。客户要够到其中任何一个，都得自己写一层补丁——那是开发者会做的事，客户永远不会做。

于是组合配置成了产品的功能清单，而没有任何人把它当成一份清单来定。每一行都是在需要它的地方被加进去的，然后就留在了落脚的地方。

打包方式是同一个形状，而它让平台丢掉了自己的升级通路。默认能力是**出厂补丁里的一行**，不是部署去选中的一个包，所以平台给某个模块发修复的唯一办法，是把整个产品发一个新版本。[`lyn-plugin-manager`](../../../../packages/boot/plugin-manager/README.zh.md) 本来就能从 registry、Git 主机、tarball 或路径安装、钉版、做版本校验并回退一个 bundle，而启动器的 `OPTIONAL_BUNDLES` 本来就能出厂自带、默认关闭且不可卸载——也就是说"可独立升级的模块"所需的机械已经存在，而默认模块是唯一没用上它的东西。

对托管产品而言，后果有两条。客户说不清这个产品能做什么，因为答案逐 profile 不同，且写在 YAML 里。以及，用插件替换了某个模块的客户没有退路：`lyn-base` 把一行设为停用，和一个 profile 从未挂载它，从外面看是一模一样的，所以"回到默认"根本不是一个存在的操作。

另外，托管产品需要而这棵树从未有过的那些模块——知识库、客户自有系统的目录、以及谁做了什么的记录——也没有一个该去的地方；否则它们只会以"再加一行"的方式，落进作者当时正在编辑的那个 profile。

## Proposal

定下一组默认模块，在每个服务于人的 profile 里全部出厂，允许插件替换其中任何一个，并保留退路。

### 十二个默认模块

其中九个已经存在，现在提升为默认：agent 终端、语言服务器、计算机操作、浏览器操作、webhook 入口、外部 harness 钩子、定时跟进、轮次交付物、运行时自修改。提升指的是出厂 profile 挂载它们，不是要写新代码：真正的工作是组合、设置界面，以及每一个各自需要的 UI。

另外三个是新的，并且进同一批，因为托管产品缺了它们就没有竞争力，而往后再加只会重犯本笔记要修的那个错：

- **知识与检索**——客户的文档，建好索引，作为工具可达。这是每个客户最先要的东西，也是今天这棵树里唯一没有任何对应物的能力。
- **连接器目录**——客户自有的系统，以 MCP 服务器的形式登记，并作为一份清单来管理，而不是作为配置。传输层已经有了；缺的是一个界面，让管理员在那里添加，让成员在那里看到已连接什么。
- **审计与用量**——做过什么、由哪位成员、花了多少。[隔离与团队](2026-10-08-agent-isolation-and-teams.zh.md)决定了用量按成员归属；这里就是那份记录被读取的地方。

运行时自修改是唯一一个可用性并非普遍的模块：它就是创造模式那项能力，[插件信任](2026-10-08-plugin-compatibility-and-trust.zh.md)决定它可以在哪里运行。它是默认模块，是在"平台出厂并维护它"这个意义上，不是在"每个部署都提供它"这个意义上。

### 默认启用，受计划与部署条件约束

每项核心能力默认启用，除非客户的计划不含它，或该部署无法安全地运行它。这两条是模块处于关闭状态的唯一理由，而且两者都要明说，不能以"没有那一行"来表达。因为没人挂载而关闭的能力是缺陷；因为计划不含而关闭的能力是一项产品决定，可以有界面把它说出来。

### 每个默认模块各自是一个出厂 bundle

默认模块是平台发布的一个 bundle，开箱即选中、不可卸载——正是 `OPTIONAL_BUNDLES` 已有的形状，减掉"默认关闭"那一半。它不是 profile 补丁里的一行。

这正是让平台拥有它给客户的那条同样升级通路的东西。模块经 [`lyn-plugin-manager`](../../../../packages/boot/plugin-manager/README.zh.md) 出厂、修复与升级，走同一套 registry 方案、同一道"下载之前先判定 LYN peer 版本"的检查、以及失败时对清单与 lockfile 的同样回滚。平台不再需要为纠正一个模块而发布整个产品，而升级节奏慢的客户仍然能收到这个修复。

它还把"替换"与"回退"合成一套机制而不是两套。客户的替换与平台自己的那一版都是 bundle，争夺同样的行，由本来就在裁决这件事的有序 bundle 列表解决。

一个模块是一个包时就是一个 bundle；跨多个包的模块出厂一个 bundle 去挂载它们，于是客户选中的单位是模块，不是它的零件。

### 插件可以替换模块，并且有退路

每个默认模块都是平台发布并维护的一个或多个插件。客户可以安装一个插件去替换它，此后也可以回到平台的那一版。

回到默认，恢复的是当前部署所运行的那个发布版本钉住的版本，而不是最近一次发布的版本——否则"回退"就是改了名字的升级，而一个为摆脱问题而回退的客户，会一脚踏上没人针对他的数据测过的版本。替换方写入的数据予以保留，并标注为由它写入，因为替换方的记录就是客户的记录，而默认模块也许无法完全理解这些记录，但悄悄丢弃它们更糟。

### 同一个运行时的两个视图

产品把同一份组合呈现两次，面向两种不同的人。

**业务视图**面向在干活的人：对话、知识、连接器、用量、设置。它用客户的说法命名能力，从不展示插件 id、profile 或补丁层。

**开发视图**面向扩展产品的人：以行呈现的组合、产出它的那些补丁层、已安装的插件及它们各自替换了什么，以及开发路径。它需要刻意进入，不是新用户起步的地方。

这不是切成两个应用。业务视图是默认界面；开发视图就是既有的设置与组合界面，只是被命名并作为独立的一处来进入，而不是混在通用设置里。

### UI 组织方式借鉴而非自创

布局沿用主流 agent harness 已经收敛到的那一套，因为客户来的时候就已经懂它：左侧栏放工作区与对话，中栏放对话本身，右侧面板放这项工作的上下文——文件、终端、浏览器、预览——以页签切换。这棵树已经有这些部件（[`ui-sidebar`、`ui-sidebar-right`，以及文件、终端、浏览器、预览面板](../../../../packages/client/ui-sidebar-right/README.zh.md)）；缺的是它们按 profile 各自摆放，而不是作为产品的布局。

默认 UI 是 lyness 自己的那一套。定制了品牌的租户，或完成了引导设置的独立部署，替换的是这套布局内部的身份——品牌，而不是摆法，依[租户级品牌](2026-10-07-per-tenant-brand.zh.md)。

### 插件开发沿用既有的 cookbook

替换默认模块的插件，就是这棵树里一个普通的包，路径也已经写好：[新增一个包](../../../../docs/cookbook/adding-a-package.zh.md)、[新增一个工具](../../../../docs/cookbook/adding-a-tool.zh.md)、[新增一张设置卡](../../../../docs/cookbook/adding-a-settings-card.zh.md)、[新增一个远程 API](../../../../docs/cookbook/adding-a-remote-api.zh.md)。开发指引要补的，是替换这件事特有的部分：模块提供的是哪个服务、替换方要提供什么才能被接受在它的位置上、以及客户回到默认时它写入的数据会怎样。

## Alternatives considered

**继续把组合当功能清单。** 不引入新概念，而且 profile 本来就能用。否决：功能清单于是逐 profile 写在 YAML 里，"已建好的"与"客户够得到的"之间那道缺口会一直看不见，直到有客户来要一件其实已经存在的东西。

**默认模块继续作为出厂补丁里的行。** 这就是今天的打包方式，保持不变不花成本。否决：它让平台除了发布整个产品之外没有别的办法发出一个模块的修复，并且让客户的替换与平台自己的那一版成为两套不同的机制，而不是同一个有序列表里的两个 bundle。

**把所有东西都挂进 `lyn-base`。** 提升起来最简单，只需看一个地方。否决：`lyn-base` 被 headless、SDK、ACP 与应用 profile 共用，而在一次 headless SDK 运行里带上 webhook 入口或右侧浏览器面板，是没人要的负担。提升属于那些服务于人的 profile。

**三个新模块以后再加。** 九项提升很便宜，新模块是实打实的工作量。否决：没有知识、没有连接器、没有审计记录的托管产品卖不出去；而推迟它们，只会让它们又停在各自作者当时在编辑的那个 profile 里——正是本笔记要修的那种失败。

**让回退拉取最新发布的默认版本。** 要跟踪的版本更少。否决：这让回退变成升级，于是为摆脱问题而回退的客户，落在一个没人针对他的数据测过的版本上。

**回退时丢弃替换方的数据。** 更干净，默认模块也不必面对它读不懂的记录。否决：那些记录属于客户，丢掉它们比保留一份默认模块只能部分读懂的数据更糟。

**一个视图加一个开发者开关。** 要建的界面更少。否决：一个视图内部的开关，让插件 id 与补丁层离业务用户只有一次点击；而这两类人要的是不同的默认，不是同一个页面藏掉几行。

**为本产品专门设计布局。** 它能精确贴合这些能力。否决：客户带着其他 harness 养成的预期而来，把新意花在"文件树摆在哪里"上买不到任何东西。

## Acceptance criteria

- 十二个默认模块在一处被列明，且每个服务于人的 profile 都挂载了其部署所支持的全部模块。
- 模块处于关闭状态，只因计划不含它或部署无法运行它；界面说明是哪一条，且没有任何模块仅仅因为无人挂载而关闭。
- 每个默认模块是一个开箱即选中、不可卸载的 bundle，且没有任何默认模块是 profile 补丁里的一行。
- 平台可以经插件管理器单独升级一个默认模块，不需要发布整个产品，且该升级通过与任何其他 bundle 相同的版本校验。
- 客户可以用插件替换某个默认模块并回到平台的那一版，且回退恢复的是当前运行发布版本钉住的版本。
- 替换方写入的数据在回到默认后仍然存在，并标注为该替换方所写。
- 业务视图不展示任何插件 id、profile 名或补丁层；开发视图作为独立的一处进入，而不是经由通用设置。
- 布局属于产品而不属于 profile：在服务于人的各 profile 之间，侧栏、对话中栏与右侧面板是同一套。
- 租户品牌或已完成的独立部署引导，改变的是布局内部的身份，而不是布局。
- 开发指引为每个默认模块写明：替换方必须提供哪个服务，以及回退时它的数据会怎样。

## Risks

**十二个模块默认启用，是一个很大的"要一直可用"的面。** 每一个都需要设置、UI、文档与测试，而一个半成品状态出厂的模块，比一个坦白缺席的模块更糟。即便整批已经定下，批内的先后顺序仍然要紧。

**三个新模块是进度上的风险。** 尤其知识与检索本身就是一个产品——摄入、索引、权限、新鲜度——把它称作十二分之一，是低估了它。

**十二个 bundle 就是十二个要分别定版的已发布包。** 每一个都多出自己的发布、自己对运行时的 peer 范围、自己的兼容面。被单独升级过的模块，就是一个"版本与组合里其余部分从未一起测过"的模块——这是"不必发布整个产品"的代价。

**回退好不好，取决于服务定义严不严。** 替换方被接受在某个模块的位置上，依据是它提供了那个模块的服务。服务定义松的地方，替换方可以既满足定义又行为不同，而回退并不会撤销这种差异写下的东西。

**两个视图会漂移。** 一项能力只加进其中一个，产出的产品就会有两个彼此不同意"存在什么"的界面。更容易编辑的那个视图会跑在前面，而那将是开发视图。

**默认启用扩大了提示词能够到的范围。** 计算机操作、浏览器操作和终端出现在每个服务于人的 profile 里，意味着 agent 的默认触达范围比今天更宽。[隔离与团队](2026-10-08-agent-isolation-and-teams.zh.md)里的约束才是让这件事可以接受的前提，所以这些提升依赖它，不能单独成立。
