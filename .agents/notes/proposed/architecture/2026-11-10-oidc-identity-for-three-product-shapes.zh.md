# Agent Note: 三种产品形态的 OIDC 身份

Status: proposed

[English](2026-11-10-oidc-identity-for-three-product-shapes.md) | 中文

## Problem

本产品以三种形态出货——SaaS 个人版、SaaS 租户版、独立部署——三者都要求人先登录才能使用产品。今天三者都做不到。

现有的是一个账户平面，却没有给企业目录之外的人留门：

- `dsh-sign-in` 持有渠道注册表与三种 kind，全是企业目录：`dsh-wecom/kind`、`dsh-dingtalk/kind`、`dsh-feishu/kind`。没有邮箱渠道，所以没有人能自助注册。
- `dsh-managed-people/directory` 在加载时就要求非空名册，`dsh-managed-people/admission` 在写入绑定之前谁都不放进来。两者都是刻意「拒绝而非放行」。
- `dsh-auth-session/store` 持久保存已登录会话，所以重启不会把所有人踢下线。
- `dsh-client-ui-sign-in` 本来就在没人登录时盖住产品——在 `uiViewer` 报告 `accounts: false` 的地方它什么都不渲染，而那是每一个没有选择 `dsh-module-accounts` 的 profile。
- `dsh-tenant` 与 `dsh-tenant-config` 是一套租户目录接缝，带静态与 HTTP 两种提供方；`dsh-module-credits` 已经按主体计量，带周期额度与预算。

所以门、会话存储、名册、租户接缝与计量都已经存在。缺的是企业目录之外的人所用的那个认证方，以及架在它之上的产品规则：自助注册、邮箱激活、不同 token 额度的用户级别，以及一个邮箱同时持有个人账户与组织账户。

决定答案形状的需求：

| 形态 | 谁创建账户 | 管理员设置什么 |
|---|---|---|
| SaaS 个人版 | 本人，用邮箱 | 平台管理员为每个人设置默认模型、用量、重置周期，以及可用模块 |
| SaaS 租户版 | 租户管理员添加坐席与用户；用户邮箱激活并自动关联该组织 | 用户级别，每级自带 token 额度 |
| 独立部署 | 只有该部署的管理员 | 用户、坐席、模型、token 用量 |

还有一条跨形态规则：同一个邮箱可以同时持有个人账户与组织账户，且该用户在 Web 端与桌面端之间切换。

## Proposal

只新增一种渠道 kind——OIDC——把认证交给身份提供方。DeepSeek Harness 继续拥有授权、名册、额度与租户关系，那才是它自己的规则所在。

为什么不自己做认证：自助注册意味着口令存储、激活与重置邮件、防爆破与防枚举、会话固定防护——都是安全敏感代码，本身没有产品价值，而且违反本仓库自己那条[优先用成熟依赖](../../implemented/process/2026-07-26-dependencies-over-hand-rolling.zh.md)的规矩（当它确实能删掉我们自有的代码时）。

三种形态随即映射到提供方自己的租户模型：

- **SaaS 个人版**——人们在本部署自己的提供方实例上自助注册；没有组织的人就是个人形态。
- **SaaS 租户版**——每个客户一个提供方组织。租户管理员按邮箱邀请；提供方负责发送与校验激活；DeepSeek Harness 收到的是一个已带组织信息的已验证主体，再由 `dsh-managed-people/admission` 把它绑到名册条目上。
- **独立部署**——客户把渠道指向自己的提供方实例，或指向他们已经在运行的目录。组成文件不需要任何改变。
- **一个邮箱两个账户**——一个身份在两个组织里。提供方只认证一次，会话携带当前活跃的是哪个组织；切换是针对另一个组织的再授权，而不是第二次登录。这正是最约束选型的那条需求，因为「一个 realm 一套用户」的租户模型无法表达它，除非在 realm 之间做身份经纪。

用户级别与额度留在这一侧：级别是名册事实，它携带的额度是一条 `dsh-credits` 周期额度。两者都不属于提供方——提供方应当只持有身份；额度有两个家，就是两个界面会各说一套。

### 分期交付

1. **渠道。** 在三种目录 kind 旁边新增一个 `oidc` kind：discovery、带 PKCE 的 authorization-code、已验证主体、组织 claim。配置渠道的那个设置页已经存在，接受一种新 kind 不需要改动。已落地为 `@deepseek-ai/dsh-oidc`，由 `dsh-module-accounts` 以 `sign-in-kind-oidc` 这一行选中。
2. **三种形态的登录门。** SaaS 两种 profile 加上 `dsh-module-accounts`，而 `dsh-client-ui-sign-in` 本来就会盖住产品；要做的是桌面端那一半与会话有效期（有效会话多久之内可以跳过登录页）。
3. **自助注册与放行。** 一条放行规则，接受提供方创建的已验证主体，使个人形态的人在首次登录时成为名册条目，而不必等管理员。
4. **级别与额度。** 名册条目上的级别，解析成一条 `dsh-credits` 周期额度；租户管理页增加级别列。
5. **账号切换。** 活跃组织记在 auth session 里，客户端出一个组织选择器，切换走再授权。

每一期都能独立出货，而且只有第 1 期是新的安全敏感面——且它全是对提供方的配置，不是我们自己的算法。

### 选型

2026-11-10 查证。公开对比恰恰在许可证这一点上互相矛盾，所以下面每一条许可证都是从项目自己的许可证文件里读出来的，而不是从对比文章里抄的：

| 候选 | 租户模型 | 被报告的许可证 | 对这组需求的契合度 |
|---|---|---|---|
| ZITADEL | organizations，一等公民 | AGPL-3.0-only；其中 `proto/` 与文档应用为 Apache-2.0，`apps/login`、`packages/zitadel-client`、`packages/zitadel-proto` 为 MIT（`LICENSING.md`） | 最契合：organizations 直接表达租户形态，以及一个身份在两个组织里 |
| Keycloak | realms | Apache-2.0 | 成熟且许可证干净，但一个 realm 是封闭用户集：一个邮箱同时在个人与租户账户里，需要在 realm 之间做身份经纪 |
| Logto | organizations | MPL-2.0；各资料对自部署版的功能限制说法不一 | 面向终端用户的登录做得好；能否自部署取决于那个限制问题 |
| Authentik | 多租户薄弱或没有 | open-core，说法不一 | 不适合租户形态 |

**推荐 ZITADEL。** 它是唯一一个租户模型能直接表达本产品需求、不需要绕路的候选，而它的许可证现在是读出来的、不是听说的：服务端为 AGPL-3.0-only。这条约束只落在服务端本身。DeepSeek Harness 仍是 MIT，通过网络以 OIDC 与它对话，因此在本仓库旁边运行未修改的 ZITADEL 不会把它的任何代码并入本仓库；义务发生在修改该服务端并再行分发时，而本计划的任何一个阶段都不做这件事。真正可能被部署方引入的客户端与协议包是 MIT，所以即便做客户端集成也仍在 AGPL 之外。若某个客户直接拒绝任何 AGPL 组件，退路仍是 Keycloak，代价是账号切换变成我们这侧的经纪工作。

## Alternatives considered

- **自建邮箱渠道。** 第 1 期否决：它就是一个认证提供方，而三种形态在任何一种可出货之前都需要激活邮件、重置、锁定与 MFA——全是提供方已经做过的工作，也全是我们可能做错的地方。
- **只保留企业目录渠道。** 否决：它完全服务不了个人形态，而且会让每个独立部署客户在任何人能登录之前先去配一个企业微信、钉钉或飞书应用。
- **每个租户一个提供方实例。** 否决：运维成本随客户数增长，而跨形态那条需求要一个身份在两个组织里可见，分开的实例表达不了。
- **把额度放进提供方。** 否决：计量已经在 `dsh-credits` 里按请求自己的主体进行，额度的第二个家就是两个会漂移的答案。

## Acceptance criteria

- 一个从未用过该部署的人用邮箱注册、验证、登录并进入产品；没有任何管理员动作。
- 租户管理员邀请一个地址；那个人激活后落在该租户的组织里、带着被赋予的级别，其 token 额度就是该级别的额度。
- 独立部署把渠道指向自己的提供方，并从组成文件放行第一个管理员，正如[独立部署指南](../../../../docs/user/guide/standalone-administration.zh.md)已经描述的那样。
- 一个邮箱同时持有个人与组织账户，在 Web 端与桌面端之间切换，不需要登录两次。
- 有效会话无需登录页即可进入产品；过期的不行。
- 三种形态在没人登录时都只显示登录页，别的什么都不显示。

## Risks

- **提供方成为登录的硬依赖。** 它宕机就是全站宕机。独立部署形态靠「指向客户已经在运行的基础设施」来缓解。
- **司法辖区，以及客户自己的许可证政策。** 在中国部署的 SaaS 可能需要提供方在同一辖区内，托管在境外的提供方可能不是一个选项。这里的 AGPL 服务端是一个独立网络服务，不是本仓库的依赖；但如果某个客户的政策禁止部署中出现任何 AGPL 组件，那正是 Keycloak 存在的理由。
- **额度与身份漂移。** 级别在这边、身份在那边，所以在提供方被删掉的人仍然持有名册条目。对账属于第 4 期的内容，不是事后再补的东西。
- **这个方案放弃了什么。** DeepSeek Harness 不再能靠自己给任何人登录：没有提供方的部署就没有入口，而今天单操作者 profile 根本不需要身份。独立部署形态只在它保留单操作者组成时才留着这条退路。
