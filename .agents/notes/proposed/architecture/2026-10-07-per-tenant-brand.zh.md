# Agent Note: 托管产品的租户级品牌

Status: proposed

[English](2026-10-07-per-tenant-brand.md) | 中文

## Problem

部署的品牌是组合配置。`lyn-host-brand-deployment` 从 profile 的补丁层读取一个 `productName`、一套调色板、一个资产目录，并在每次渲染 index 时把结果写进 `globalThis.lynDeploymentBrand`。因此一个进程恰好服务一个品牌——私有部署正是这个形态：运行服务器的运营方就是品牌所有者，而[配置优先于用户设置](../../implemented/architecture/2026-08-04-configuration-source-ownership.zh.md)正是让他们的身份不被使用者改掉的那条规则。

托管产品不是这个形态。一个进程服务许多客户，每个请求由 [`lyn-tenant-request`](../../../../packages/tenant/tenant-request/README.zh.md) 从 header、hostname 或子域解析出租户。企业计划的客户期望产品带着他们的标志、名称与色彩；个人计划的客户不期望这些，也不能把平台的署名撤掉。今天这两件事都无法表达：`TenantConfig` 已经带有 `displayName` 和 `copy` 覆盖表，所以租户能改文字，但一切视觉——标志、字标、favicon、调色板——都来自那一行宿主配置，对该进程服务的每个租户完全相同。

缺口不只是字段。有三处机制假定只有一个品牌：index 注入在任何租户被识别之前就已解析完毕、品牌资产从一个目录经一个 URL 提供、`showPoweredBy` 是运营方设置的普通布尔值。只加字段而不动这三处，会把一个租户的图形发给另一个租户。

## Proposal

把品牌变成租户对自己的配置的一部分，按请求解析，并由租户的计划决定他能否更改。

### 品牌成为租户配置

`TenantConfig` 在 `copy` 旁边新增 `brand` 成员：三个产品名、该租户替换的调色板令牌、三张资产各自的引用。规则沿用既有的——名字用 `isBrandName`，调色板用 `BRAND_COLOUR_TOKENS` 与 `isBrandColour`——统一写在 `validateTenantConfig` 中，只读存储在加载时检查，可写存储在保存前检查。没有新的东西来定义"什么是可用的品牌"。

三个名字作为一组解析，与页面上的规则相同：租户给出其中任一个，另两个取它；三者都不给，取平台的。同一规则再上一层——租户品牌覆盖部署品牌，部署品牌覆盖内置的 lyness 取值——因此配置了一半的租户不会读成自己的名字与平台名字的混合体。

### index 注入按请求解析

`brand-deployment` 仍然拥有注入，但不再是它唯一的来源。品牌跟随请求**所行事的**那个组织，由[行事上下文](2026-10-08-people-memberships-and-acting-context.zh.md)给出：解析出组织的地址把上下文约束在该组织上，而平台自己的地址则从当前生效的上下文取得组织。当该组织配置了品牌时，注入的是它自己那份；否则仍是部署那份。

仅凭地址解析，对从未启用子域的组织是错的：它的成员访问的是平台地址，那里的 hostname 不指向任何人，于是他们会在为自己组织行事的同时看到平台的品牌。客户端无需改动：它本来就只从页面全局读一个对象，而 [`brand-values.ts`](../../../../packages/client/locale/src/client/brand-values.ts) 本来就把每个成员当作不可信的页面数据来校验。

### 资产按租户寻址

品牌资产从"一个目录、`/brand/<文件>`"改为"按租户存储、`/brand/<tenantId>/<文件>`"，URL 带内容哈希，缓存条目以哈希为键长期有效。路径里没有租户，一个客户浏览器的缓存就能回答另一个客户对 `/brand/mark.svg` 的请求；没有哈希，被替换的标志会继续从服务器够不到的缓存里被取出。

### 修改品牌是产品界面，不是命令

租户管理员在产品自己的设置里修改品牌，调用 `tenant.save()`。`brand-setup` profile 保持原样：面向私有部署、从服务器自己的终端进入的单运营方工具。

### 计划决定，服务端执行

租户既有的 `features` 列表里的两个条目承载这个决定：

- `brand.customize`——设置界面出现，`brand` 的保存被接受。个人计划的租户两者皆无。
- `brand.remove-attribution`——才允许把 `showPoweredBy` 关掉。没有它，署名无论租户要求什么都保留，因此个人计划的租户在 [`sidebar.attribution`](../../../../packages/client/ui-sidebar/README.zh.md) 席位上始终显示 `Powered by lyness`。

两者都在 `tenant.save()` 内部执行。设置页面隐藏控件只是呈现；决定属于做出它的那个操作，因为一个直接的 Remote 调用到达的是同一个保存。

### 寻址：先做子域，自有域名以后再说

租户以 `<slug>.<基础域名>` 访问，`tenant-request` 已经能解析。`agent.acme.com` 这类自有域名刻意不在范围内：它们经由同一个接缝解析，但会带来证书签发、续期与所有权证明，那是另一摊工程，且与品牌如何存储和解析无关。

## Alternatives considered

**一个租户一个进程。** 每个客户一套部署，今天的宿主级品牌原样可用。否决：托管产品的成本结构建立在共享进程之上，而且这会让其余所有租户级能力——模型、供应商、功能——失去意义，它们存在的前提正是一个进程服务多个租户。

**把品牌放进 `copy`。** 名字属于文案，租户本可以通过既有的覆盖表来改。否决：它覆盖不到任何视觉，调色板得不到校验，且任何 copy id 都能冒充品牌字段。品牌有自己的规则和自己的资产，所以它拿到自己的成员。

**租户上一个 `whiteLabel` 布尔值。** 比两个 feature 条目简单。否决：它把两个在业内一律分开定价的决定混为一谈——带上自己的标志，和移除平台的署名——而后者恰恰是客户最先要求的那个。

**客户端启动后再取品牌。** 页面可以调用 `tenant.describe()`，拿到后再应用品牌。否决：品牌会在首次绘制之后才到达，于是每次加载都会先闪过平台的身份。

**允许租户上传字体。** studio 在授权确认之后接受品牌方自有字体。在托管产品上否决：平台将基于上传者的保证去分发字形。如果确实需要字体控制，退路是提供一组已授权字体供选择。

## Acceptance criteria

- `TenantConfig.brand` 存在，`validateTenantConfig` 拒绝不可用的名字、未知的调色板令牌与不可用的颜色，且拒绝信息指明是哪个字段。
- 为带品牌的组织行事的请求，其 index 注入得到该组织的品牌，无论该组织是由地址还是由行事上下文指明的；为不带品牌的组织行事、或不为任何组织行事的请求，得到部署品牌；没有部署品牌时得到内置的 lyness 取值。
- 配置了不同标志的两个租户收到不同的资产字节，且任一 URL 都无法回答另一个。
- `tenant.save()` 拒绝来自不具备 `brand.customize` 的租户的 `brand` 变更，拒绝来自不具备 `brand.remove-attribution` 的租户的 `showPoweredBy: false`，两者都发生在 Remote 调用处而不是页面上。
- 个人计划的租户渲染署名行，无论其存储的配置写了什么。
- `brand-setup` profile 与私有部署路径的行为与此前完全一致。

## Risks

**一个租户的品牌泄漏到另一个租户的页面。** 整套设计系于"请求在 index 渲染之前解析出正确的租户"。缓解在于该解析已经存在且有测试；新工作不得在它前面加缓存。index 响应绝不能跨租户共享。

**资产存储增长。** 每个租户三个 SVG 很小，但被替换的资产若无人清理就会堆积。被取代的资产需要在写入时就有归属，而不是事后扫一遍。

**两条路径的校验漂移。** 私有部署在加载时校验，托管产品在保存时校验。两者必须调用同一个 `validateTenantConfig`；规则出现第二份副本，正是一条路径开始接受另一条拒绝之物的方式。

**署名的执行只覆盖页面这条路。** 如果以后出现任何不经 `tenant.save()` 就写入租户配置的界面，计划门禁便不再生效。保存是执行点，必须保持为唯一的写入者。
