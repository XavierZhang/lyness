# Agent Note: 人、成员身份，以及一次调用所行事的上下文

Status: proposed

[English](2026-10-08-people-memberships-and-acting-context.md) | 中文

## Problem

这棵树里没有任何东西认识"人"。[`lyn-tenant-request`](../../../../packages/tenant/tenant-request/README.zh.md) 把一次调用解析到一个组织——靠网关设置的 `x-tenant-id` 头、靠 hostname、或靠基础域名下的子域标签——到此为止。唯一像用户的标识是 [`anonymous-user-id`](../../../../packages/identity/anonymous-user-id/README.zh.md)，而它存在的目的是在**不识别任何人**的前提下关联遥测。`TenantConfig` 记录一个组织的模型、供应商、功能与文案，它自己的 README 也写明了这个缺口：组织与 agent 之间没有用户层。

已经有两份提案依赖这一缺失的层。[会话归属](2026-10-07-session-ownership.zh.md)要求每次调用说明是谁打开了对话、以及他以哪重成员身份行事。[租户级品牌](2026-10-07-per-tenant-brand.zh.md)要求有一位可以更改品牌的租户管理员，以及一道在保存处执行的计划门禁。两者都不能先建。

而且仅仅解析出组织也不够，原因是地址解决不了的：一个人只有一个身份，却可以同时持有多重成员身份——他自己的，以及他所属的每个组织各一个。没有启用子域的组织，访问的是平台自己的地址，那里的 hostname 根本不指向任何组织。所以"这次调用是为哪个组织发出的"一般而言无法由地址回答，也无法由此人的成员关系回答，因为可能有好几重。

## Proposal

一个人是一个身份。变化的是他所行事的上下文，而每次调用都要说明它。

### 一个身份，多重成员身份

一个人登录一次、持有一个身份。**成员身份**是此人在某一个组织中的身份，且恰好携带一个角色。一个人可以持有自己的个人上下文，外加他所属的每个组织各一重成员身份；此人自身不说明此刻哪一重在生效。

角色共三级，目前不再增加：

- **平台管理员**——属于平台，不属于任何组织；
- **租户管理员**——管理一个组织；
- **成员**——在一个组织中工作。

只读的审计员角色考虑过并推迟：在还没有任何界面要求它之前就增加一个角色，这个角色往往哪里都没有被执行。

### 行事上下文存在于已认证的会话里

登录产生的是**人**的会话，不是某重成员身份的会话。该会话携带当前生效的上下文——个人，或某一重成员身份——作为服务端状态，只能由一次显式的切换改变。它绝不从"此人恰好属于哪些组织"推断而来。

每次调用都说明自己的上下文，服务端校验该上下文确属调用者。不说明上下文的调用被拒绝，而不是取默认：一个持有两重成员身份的人会让默认变成猜测，而此处猜错的代价是把一个对话归到错误的组织名下。

### 地址约束上下文，但不选择上下文

地址解析继续做它原本做的事，并对结果增加一条规则：

- 在解析出某个组织的地址上——该组织自有的 hostname，或它在平台基础域名下的子域——行事上下文**必须**是该组织的一重成员身份。其他上下文一律拒绝，而不是静默切换。组织因此获得一个"我的人只以我的身份行事"的空间，该空间显示的品牌也不含糊。
- 在平台自己的地址上，没有解析出组织，此人持有的任何上下文都允许。上下文以个人身份开始，并记住该地址上一次使用的上下文。

这样一条规则同时回答了"启用了子域的组织"与"没有启用子域的组织"，而不是两套机制。

### `x-tenant-id` 保持为基础设施

该头是部署前方的网关设置的，优先级高于 hostname。托管部署**必须**在边缘剥离客户端送来的同名头。否则任何已登录的人都能声称任何组织，整条边界形同虚设。这是托管产品的部署要求，不是可选项。

### 新组织的第一位管理员由平台指派

组织不能自举出自己的管理员。入驻完成时，由平台管理员为该组织指派第一位租户管理员；此后组织才能自行配置与管理，包括邀请成员与结束其身份。该规则因被依赖而记录在[会话归属](2026-10-07-session-ownership.zh.md)中，而本笔记拥有它。

### 结束身份，结束的是成员身份而不是这个人

把一个人移出组织，或回收他占用的席位，结束的是那一重成员身份。此人保留自己的身份、个人上下文，以及该组织之外他拥有的一切。他在该组织中的对话留在原处、归属不变，并读作已归档——这一点由[会话归属](2026-10-07-session-ownership.zh.md)规定。

### 平台管理员不能做什么

平台管理员创建组织、指派第一位租户管理员、管理组织购买了什么。指派管理员不等于成为成员，而上述权力中没有一项包含读取组织的对话。企业客户对一个托管 agent 平台提出的第一个问题是"谁能看到我们的工作"，这个答案必须是设计的属性，而不是一句承诺。

## Alternatives considered

**一个组织一个账号。** 此人为每个组织分别登录。否决：它为一个人增殖凭据，把切换变成一次登出，并使平台无法断定两个账号是同一个人——而当组织回收席位时，这一点立刻要紧。

**仅由地址携带上下文。** 在组织有子域时很优雅。否决：没有启用子域的组织访问的是平台地址，那里不指向任何组织，于是该规则对最常见的情形无解。

**从此人的成员关系推断上下文。** 当一个人恰好只属于一个组织时很方便。否决：一旦他属于两个，它就是猜测，而猜错的代价是一个对话被归到错误的组织名下——还是在一份永不重写的记录里。

**客户端上下文选择器，服务端不存状态。** 客户端送来上下文，服务端信任它。以该形式否决：服务端无论如何都要对照调用者的成员关系做校验，因此状态应当与校验在同一侧。客户端仍可以显示选择器，只是它不拥有答案。

**增加第四个只读审计角色。** 以后有用。推迟：目前没有任何界面要求它，而先于消费者出现的角色往往哪里都没有被执行。

## Acceptance criteria

- 一个人持有一个身份与任意多重成员身份；每重成员身份恰好携带三种角色之一。
- 不说明上下文的调用被拒绝；说明了调用者并不持有的上下文的调用被拒绝。
- 在解析出组织的地址上，以其他任何上下文行事的调用被拒绝，而不是被切换。
- 在平台地址上，一个人可以以他持有的任何上下文行事，而新会话以个人上下文开始。
- 在托管部署中，客户端送来的 `x-tenant-id` 永远到不了租户解析。
- 新入驻的组织在平台管理员为其指派第一位租户管理员之前，自己什么也做不了。
- 结束一重成员身份后，此人的身份与个人上下文完好无损。
- 平台管理员的任何操作都不读取组织的对话。

## Risks

**一次登录横跨多个地址。** 一个人在平台地址登录后再打开某组织的子域，不应被要求重新登录，而该凭据也不得在组织从未授权的地址上可用。Cookie 作用域与集中登录是它们自己的工作，本笔记不设计。

**边缘成为安全关键。** 剥离 `x-tenant-id` 是一个部署步骤，这意味着这条边界依赖本仓库之外的东西。忘记这一步的部署看不到任何报错——系统照常工作，只是为错误的租户工作。

**切换是客户端会缓存的状态变化。** 客户端持有在某个上下文下取得的数据、随后切换，期间存在一个窗口，它会把一个组织的数据显示在另一个组织的名字之下。客户端必须在切换时丢弃按上下文取得的状态——这是一条服务端校验无法强制的客户端规则。

**角色会被要求增加。** 三个角色对现有的东西够用；第一个带合规团队的真实客户就会要第四个。这个形状必须让"增加一个角色"成为命名问题，而不是重新决定执行点在哪里的问题。
