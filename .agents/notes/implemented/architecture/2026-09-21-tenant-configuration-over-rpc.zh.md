# Agent Note：租户通过已有的 Remote 命名空间配置自己

状态：已实现

[English](2026-09-21-tenant-configuration-over-rpc.md) | 中文

## 问题

租户配置能力缝已经可以在进程内读写，持久化后端也接受保存，但没有任何东西把二者暴露给浏览器。需求文档为此提议了一套 REST 界面——那会是本部署已在提供的 Typert Remote 命名空间之外的第二套传输：第二条认证路径、第二套错误词汇，以及第二个需要与能力缝保持同步的东西。

更难的那一半是授权。配置界面必须知道自己被问的是谁的配置，而看起来最直接的答案——加一个租户 id 参数——根本不是答案：能指名自己租户的调用方也就能指名任何租户。

## 决策

`@lyness/lyn-api-tenant-controller` 注册 `tenant` Remote 命名空间，含两个方法。`describe` 答复调用方租户自己的配置，外加能力缝本身不携带的两个事实：`writable`（本部署的后端是否接受保存）与 `configured`（该租户是否保存过任何东西）。`save` 整份替换配置，其输入不携带租户 id。

四条裁定决定了它的形状。

**用 Remote，不用 REST。** 与需求文档的冲突按「已有的传输」裁定：一道认证围栏、一个生成的客户端、一套错误词汇，以及一份由编译器对着能力缝检查的契约。REST 界面得把这些全部重述一遍。

**租户来自请求，绝不来自参数。** 两个方法都读 `ctx.requestTenant`，调用没有命名租户时以 `tenant/unresolved` 拒绝。这同时也是目前能拿到的全部授权故事：部署有组织但没有成员，因此「调用方只能配置自己的组织」是唯一有东西可据以强制的规则。

**刻意校验两遍。** wire 字段在这里解析，能力缝自己的 `validateTenantConfig` 也在这里跑一遍，因此调用方在一次答复里收到全部问题，表单能一次标出所有字段。后端还会为它自己的其他调用方再校验一遍；这份重复正是把规则放在能力缝里的意义。

**答复从存储回读，而不是拿输入回声。** 存储才是「自己留下了什么」的权威。信任回声的界面会显示它发出去的东西——那与一次成功保存完全无法区分，直到下一次重新加载。

## 考虑过的替代方案

**按需求文档做 REST 界面。** 对 web 团队更熟悉，也能用 curl 调。但它会重复认证、错误映射，以及 Remote 生成器本可从 Host 签名推导出的请求／响应类型；而本产品里没有任何调用方是「只能调 REST、不能调命名空间」的。

**把租户 id 作为参数，再对着请求做授权。** 运营方可以用同一个方法代表另一个租户操作。但这会给每个方法都加一道检查，漏掉一处就静默变成跨租户访问；而目前也还没有可供授权的运营方角色。

**像 settings 命名空间的 `mutate` 那样做字段级变更。** 页面可以只保存一个勾选框。但能力缝的规则是整份配置的规则——默认模型必须在其可用清单内、模型的供应商必须已授权——字段级写入要面对一份自己看不见的配置。

**直接返回能力缝的 `TenantConfig`，不做视图。** 投影代码更少。但授权中的凭据在 Host 侧是带标记的引用，而读取还需要能力缝不携带的事实；直接透传要么把带标记的类型漏到 wire 上，要么答复里没有 `writable`——而那正是页面最需要的字段。

**顺便暴露租户清单，让界面能列出租户。** 管理后台将来会需要。但列出租户是另一种权限——跨组织的权限——而目录是刻意只回答「指名的对象」的。

## 影响

管理界面现在可以读取并保存一个租户的配置。它仍然做不到的是：创建租户、列出租户、保存凭据引用背后的密钥；那些分别属于目录与凭据库自己的界面。

组织内部谁有权保存，目前不受强制。任何已认证且能解析到某个租户的调用方，都可以保存该租户的配置。这一点写在包 README 的限制里，而不是藏起来；相应的检查会随用户记录一起落地。

本命名空间没有进任何已发布 profile。它只有在同时挂载了目录、配置存储与每请求作用域的部署里才可达；把它挂进 `web-app` 会广告一个总是拒绝的命名空间，并在还没有页面使用它之前就改变客户端的生成面。

`ctx.tenantController` 与其他租户服务一样需要在同一批生成器表里手工登记，`CUSTOM.md` 已记录。
