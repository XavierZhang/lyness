# Agent Note：租户配置自己的模型，且绝不借用部署方的

Status: implemented

[English](2026-09-20-tenant-configuration-seam.md) | 中文

## Problem

解析出请求属于哪个租户，并没有回答那个租户能做什么。上游按部署存模型设置——每家供应商一段设置，密钥存在操作系统用户的凭据库里——这对"一台部署一个组织"是对的，对多个组织则不可用：同一部署上的两个组织会共用一份模型清单与一把密钥，用量也会变成一张没人分得清的账单。

身份在另一个方向上有同样的空缺。组织希望自己的规则与语气出现在其成员发起的每个请求里，个人希望有自己的，Agent 也希望有自己的——三层，而它们都没有安放之处。

## Decision

`ctx.tenantConfig` 读取一个租户为自己配置的内容：按模态的模型（语言、图片、视频、音乐）、通过哪些供应商使用它们、可用的功能、它贡献的身份文本，以及它覆盖的界面文案。`@lyness/lyn-tenant-config-static` 从组合配置提供它，`@lyness/lyn-tenant-http` 消费它，在原有答复上加入发起请求方的功能与文案。

四条裁决决定了它的形状。

**任何东西都不回落到部署方。** 没有配置的租户读作 `undefined`，空的模型清单表示该模态不可用。回落会让租户花掉一个自己从未选择的账号，并把两个组织的用量记在同一张账单上。

**授权携带凭据引用，而不是密钥。** 值留在凭据库里，因此配置可以被读取、记录与导出而不携带任何密文；两个租户通过指向不同引用实现隔离。授权还可以带自己的 `baseUrl`，租户接入自建模型走的就是这条路——与使用托管供应商是同一条路径。

**约束叠加，个性替换。** 身份是两个字段而不是一个，因为二者的合成方向相反。规则沿各层累加——平台、组织、用户、Agent——下层删不掉上层，因此组织的合规规则不会被一个写着"忽略以上要求"的 Agent 抹掉。语气则相反：声明了自己语气的 Agent 取代组织的。

**后端说明自己能否被写入。** `capability()` 返回 `read-only` 或 `writable`，管理界面据此显示或隐藏保存，而不是靠失败去发现。本次交付的后端是只读的；可写的那个随持久存储到来。

## Alternatives considered

**复用上游按部署的设置段。** 不需要新的能力缝，现有的模型设置界面也能照常工作。但那些段按供应商分键，不按租户，而它们的密钥属于操作系统用户——没有任何键可以挂上第二个组织。

**把供应商密钥写进配置。** 一处就能读到租户的全部设置。但配置会被读取、记录、diff 与导出；写进去的密钥也就出现在这些地方。

**把配置放进租户目录里。** 只要一个服务而不是两个，请求解析到租户时配置也一并带上。但目录按请求作答，配置由管理员编辑；两者生命周期不同、后端不同，等存储到位后写入路径也不同。

**身份只用一个文本字段。** 存储与编辑都更简单。但单字段意味着 Agent 层会改写组织写下的一切，而这正是拆成两个字段要防止的合规失败。

**现在就交付可写后端。** 管理界面立刻就能保存。但写入需要按租户的持久存储，那是另一项决定；现在先声明这项能力，可以让那个界面一次写对，面对的能力缝已经能说明哪些后端接受保存。

## Consequences

身份只有形状。目前没有任何东西把各层合成进提示词，因为进入模型请求的内容必须能从会话日志重建，而记录"本会话运行于哪份身份"的会话事件是另一项工作。组织与 Agent 之间的用户层要等用户记录，本部署尚无。

功能是租户可用的 id，不是成员持有的权限。角色需要成员，而本部署没有成员。

不鉴权的租户路由现在会答复发起请求方的功能与文案。模型、授权与凭据引用不在其中；需要它们的界面必须鉴权。

`ctx.tenantConfig` 与 `ctx.tenants` 一样，要在同一批生成器表里手工登记——子系统页、类型页、能力缝角色、类型等价清单——`CUSTOM.md` 记录了它们。
