# Agent Note：一个请求属于哪个租户，以及承载它的钩子

状态：已实现

[English](2026-09-21-the-tenant-of-a-request.md) | 中文

## 问题

Remote 方法收到的是端点、载荷与调用方的取消信号，不包含它到达时的那个请求。对一个「只回答调用方问了什么」的命名空间来说这是对的，但也让「发起调用的组织」无处安放。

由此产生两个后果。会话戳记只能从自己的配置里取租户——那是整个进程的一个值，因此只对服务单一组织的部署成立，这也是它写下的记录当时要附带一句说明的原因。而配置界面则没有诚实的办法知道自己被问的是谁的配置：租户不能作为方法参数，因为能指名自己租户的调用方，也就能指名任何租户。

## 决策

Connection 新增一个扩展点：`ctx.connection.rpc.scope(scope)` 包裹所有通道上的每一次已解码调用，接收 HTTP 请求，并且必须调用 `run()` 且原样返回其结果。`@lyness/lyn-tenant-request` 注册一个这样的作用域，按与 HTTP 路由相同的顺序解析租户——请求头、主机名、子域名——并在调用期间以 `ctx.requestTenant` 发布该租户及其配置。

四条裁定决定了它的形状。

**作用域决定上下文，绝不决定结果。** 它不得返回另一个结果，也不得跳过分发。一个能做到这两件事之一的钩子，会把所有通道上的每个端点都变成其持有方未曾写下的东西——那是比本次所需大得多的改动。

**配置与租户在同一步解析。** 最需要它的消费方是 `session/created` 监听器，它是同步的，无法等待存储。趁调用仍处于异步阶段把两者都解析出来，才使同步读取成为可能；两个已发布的后端都从内存作答，因此代价是每次调用一次 map 查找。

**解析不到租户的调用不在这里被拒绝。** 哪些调用可以在没有租户的情况下继续，是应答那一端的决定——触及某个组织数据的命名空间会拒绝，不触及任何组织的调用无需知道。在作用域里拒绝，会让每个端点都变成「仅限租户」，而挂载一个目录并不意味着这件事。

**读取面由一个不导入 Connection 的模块定型。** `ctx.requestTenant` 的类型是 `./types` 里的接口，因此同样跑在 headless 下的会话戳记，可以读取调用方租户而不必按 web 传输编译。

## 考虑过的替代方案

**把请求传进 `ConnectionRpcHandler`。** 只多一个参数，不必推理嵌套。但这会改动每个通道持有方都要实现的签名，并把传输层的事实交给每个命名空间，而不是交给唯一以传输策略为职责的那个插件。

**用 handler 收到的 `AbortSignal` 作为每次调用状态的键。** 完全不需要改上游。但 Gateway 会派生信号，handler 看到的身份不一定就是传输层创建的那个；一次静默落空的查找会把会话归给没有租户、或归给错误的租户，事后也无从查证。

**在 Gateway 的路由前再注册一条 `/api` 路由。** 同样不改上游。但 web server 每个路径只选一条路由，路由与其 handler 之间没有可站的位置；而共享通道只容纳一个 interceptor，那个位置属于 Gateway。

**让每个租户相关的 Remote 方法都带一个租户参数。** 不需要作用域，不需要 async-local 状态，契约也显式。但那样调用方就自己指名它要代表哪个租户——正是整条能力缝要堵上的授权漏洞。

**保留配置的租户，会话仍按它打戳。** 不需要新包。但它对服务多个组织的部署不可能正确，而这正是本次工作面向的部署。

## 影响

会话记录现在写的是创建该会话的那次调用所属的租户；只有在没有调用时才写配置的租户——CLI 运行、恢复的会话、子 Agent。正因为这些情形，`lyn-tenant-session` 的 `tenantId` 仍然必填。

作用域覆盖的是一元 RPC。Remote 流与 `/api` 下的精确 Fetch 路由走另外的分发路径，看不到租户；这些路径上需要租户的界面必须自己解析，做法与 HTTP 路由相同。

`x-tenant-id` 是被信任的——在 HTTP 路由上本来也是。把 `/api` 暴露给不受控调用方的部署，必须在自己的边缘终结这个请求头。

钩子落在上游的 `rpc.ts` 与 `rpc-host.ts`，已记入 `CUSTOM.md`。树里没有其他地方注册作用域，因此不挂载任何租户行的部署跑的还是原来那条分发路径，只多了一次遍历空集合的函数调用。
