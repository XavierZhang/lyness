# Agent Note：会话日志携带租户及其运行时所用的身份文本

Status: implemented

[English](2026-09-20-tenant-in-the-session-log.md) | 中文

## Problem

服务多个组织的部署，必须能在会话结束很久之后说清那是谁的会话。而日志里没有任何东西记录这一点。

身份的要求更严。租户会为自己的模型请求贡献约束与语气，而本仓库的既有规则是：进入模型请求的内容必须能从会话日志重建。租户会修改自己的配置；只记录租户名的日志，在配置被改之后，重建出的会话将带着该会话从未使用过的文本。

最显然的安放之处是封闭的。`SessionHeader` 是从一份封闭白名单里逐字段拷出来的固定字段表，物理 JSONL 头部又会拒绝其字段集之外的任何键，因此往那里加字段属于结构性格式变更：要升 `SESSION_FORMAT_VERSION`，并新增相邻的迁移包。

## Decision

一条仅日志事件 `tenant/identity`，由 `@lyness/lyn-tenant-session` 在 `session/created` 时为每个会话追加一次。它携带一组带版本的显式字段——租户 id、创建时读到的标识，以及该租户的约束与个性原文。新增事件类型不需要升格式版本；逐事件的 `ignorable` 守卫覆盖了词汇增长。

身份文本按原文记录，而不是按引用。仓库对"记录进入过模型的内容"有两种形态——文本本身就是那个东西时记原文，可解析时记可解析的 id——而租户身份属于前者：它来自可变的配置，因此 id 解析不出该会话实际运行时所用的内容。

`tenant` 会话投影把记录折叠回来，其状态同时是幂等守卫：折叠结果已含记录的会话不再被写入，因此 fork 与被恢复的会话保留其创建时的戳记。

租户来自插件配置，一个部署一个。会话创建不携带租户：浏览器的创建调用以载荷形式过线，网关不带请求头地分发它，而租户只在存在原始请求头的地方才可知。要让那个请求的租户抵达会话创建，需要改动创建请求类型、Remote 方法与浏览器端——三个上游文件——那可以等到管理界面本来就需要它们时再做。

## Alternatives considered

**把 `tenantId` 放进会话头部。** 那里正是会话不可变事实的居所，且所有读者本就解析它。但头部的逻辑形状与物理形状都是封闭的，因此这属于结构性变更：升格式版本、新增迁移包、重切所有保留的快照代际——只为一个用事件同样能持久记录的字段。

**只记录租户 id。** 事件更小，而租户当前的身份只需一次查询。但查询答复的是租户**现在**的配置；会话运行于它**当时**的配置，而两者之间的差异正是审计要问的。

**记录身份文本的哈希。** 既能证明用的是哪段文本，又不必存两份。但没有任何第一方插件记录哈希，哈希也无法被读回成提示词；而文本原文本就在日志里（在组装后的系统提示词中），哈希只会证明它与一段读不出来的东西一致。

**现在就把租户放进会话创建请求。** 戳记将按请求而不是按部署，这正是 SaaS 所需。但它要改三个上游文件，本 fork 此后每次合并都要承担；而将来需要同一套管线的管理界面尚未落地——晚一点一次改完，比现在改一次、将来再改一次更省。

## Consequences

对服务单个租户的部署，戳记是正确的；对服务多个租户的部署则不完整：每个会话记录的都是配置里那个租户。部署不得把本插件当作能区分租户来组合。

身份在插件启动时读取一次。只读的配置后端本就无法在进程运行中变化，因此这与部署今天真正能做的事相符；将来可写的后端需要重新读取。

没有任何随附 bundle 组合租户插件，因此录制会话快照不受影响。把它们加进 Web 应用 bundle 会改变所有参与比对的场景所产出的日志，那意味着要在同一次改动中刷新快照语料与两个 SDK 投影。
