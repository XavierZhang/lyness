# Agent Note：租户配置改为保存，而不是改文件再重启

状态：已实现

[English](2026-09-21-durable-tenant-configuration.md) | 中文

## 问题

租户配置能力缝已经声明后端要说明自己能否被写入，但当时只有只读后端。修改一个租户的模型、供应商授权、功能、身份或文案，都要改部署的补丁层再重启——管理界面做不到，运营方也不该为一次日常修改这么做。`capability()` 存在，却没有任何后端会回答 `writable`。

## 决策

`@lyness/lyn-tenant-config-store` 在存储域之上注册 `ctx.tenantConfig`：每个租户在 `tenant_config` 存储域中占一条记录，版本 1，布局 `per-record`。它报告 `writable` 能力，写入前先用能力缝自己的 `validateTenantConfig` 校验，并且自身不接受任何配置——记录本身就是配置。

三条裁定决定了它的形状。

**是记录而不是行，且不能并存。** 两种后端是二选一：能力缝在一个 context 中只容纳一个存储，因此部署要么挂载从组合配置读取的那个，要么挂载这个。把它们叠起来就要逐字段裁决谁优先，而一半在补丁层、一半在数据库的配置，运营方在部署启动前无法 diff。

**用 `per-record`，而不是单一文档。** 部署中的租户是逐个写入、逐个可弃的。保存一个租户的配置不能重写其他租户的：并发保存会丢掉对方的写入，一份损坏的文档也会带走整份清单。

**在写入前校验，而不是在读取时。** 违反规则的保存会被拒绝，并一次列出全部问题，便于表单一并反馈。另一种做法——先存下来、之后失败——会把错误暴露在供应商请求处，离制造它的管理员很远。

## 考虑过的替代方案

**让从组合配置读取的后端自己写补丁层。** 只有一个后端，运营方也仍然保有一份可读文件。但让运行中的进程写组合配置，会让这个文件同时是输入与输出：保存会与加载器竞争，手工编辑与保存互相覆盖，且无从判断谁在后。

**用专用 SQL 表而不是存储域。** 可以对租户做带索引的查询，迁移故事也更熟悉。但存储域层已经拥有版本管理、后端路由与读取时的 schema 校验；专用表要把这三件事重做一遍，还会把存储绑死在一种介质上——而私有化部署想要 JSON 文件，SaaS 部署想要 SQLite。

**字段级更新。** 管理界面改一个勾选框就只写一个字段。但能力缝的规则是整份配置的规则——默认模型必须在可用清单内、模型的供应商必须已授权——字段级写入要面对一份自己看不见的配置。读出、修改、整份保存能让每次保存都可校验。

**保存后通知消费方。** 读到旧配置的界面可以自行刷新。但目前没有任何消费方在热路径上读取配置，而没有订阅者的事件，会提前买下一份会话日志义务与兼容承诺。

## 影响

管理界面现在可以保存了。它在这里做不到的是创建或保存租户的密钥：记录只指明凭据引用，写入该引用背后的值属于凭据库自己的界面。

已读过配置的消费方不会在保存替换它时收到通知，需要再读一次才能看到新值。目前没有消费方持有配置到让这件事产生影响的程度。

本存储没有被任何已发布的 profile 挂载。要挂载它的 profile 同时也需要一种介质与一条存储域路由，而这是每个部署自己的组合决策；在管理界面出现、能通过它保存之前，已发布的 profile 继续使用只读后端。

`ctx.tenantConfig` 不需要新增生成器表项——能力缝已经登记过了——但本包需要登记 Host 编译面引用、模型体验判定，以及能力缝的实现清单，均已记入 `CUSTOM.md`。
