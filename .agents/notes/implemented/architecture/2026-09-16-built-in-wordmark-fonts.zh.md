# Agent Note：平台随附字标所用的字体

Status: implemented

[English](2026-09-16-built-in-wordmark-fonts.md) | 中文

## Problem

排版字标需要调用方提供字体文件，因此 brand-studio 没有字体就无法运行，而不上传任何文件的 SaaS 租户根本无法拥有字标。名称还必须在客户所用的任何语言下完整排出：没有单一字体能同时覆盖拉丁字母、希腊文、西里尔文与中日韩，而原先的排版器会拒绝字符不全在同一字体中的名称。

随附字体又撞上仓库的许可证策略。`scripts/gen-third-party-notices.ts` 不接受非宽松许可的运行时 npm 依赖，而 SIL Open Font License 不在它的宽松许可集合里。它也完全没有安放「提交在包内的第三方文件」的位置：它披露 npm 依赖、vendored 包、Python 依赖与 pnpm 补丁，而字体文件哪一类都不是。

## Decision

`@lyness/lyn-host-brand-fonts` 按 OFL-1.1 原样随附两个字体文件——Inter SemiBold 4.1 与 Noto Sans CJK SC Medium 2.004——许可证文本随附在旁，并按回退顺序暴露它们。它们只服务于品牌字标：文件在 host 上读取，字标以轮廓形式分发，因此没有任何字体到达浏览器，平台也不以网页资源形式分发字体。

`typesetWordmark` 现在接收一组字体。它把每个字素簇分配给第一个能绘制它的字体，空白字符留在它前面那一段里，并以 em 为单位计算几何，使每 em 单位数不同的字体共用一个缩放比例。Inter 排在前面，因此即使 Noto Sans CJK 也能绘制拉丁字母，拉丁字母仍保持 Inter 的字形。运营方不传 `--font` 时，`brand-studio` 使用内置字体。

披露走的是新机制，而不是对 npm 机制开例外：包在 `third-party-assets.json` 中记录每个提交进来的第三方文件，生成器逐条校验——文件与其许可证文本存在、文件仍匹配其 SHA-256、许可证为宽松许可或字体的 OFL-1.1——拒绝任何未被记录列出的字体文件，并把它们列进 `THIRD_PARTY_NOTICES.md`。

## Alternatives considered

**依赖 `@fontsource` 系列包。** 它们是 npm 包，现有披露机制加一条按精确包名的许可授权即可覆盖。但它们的中日韩包每个解压后有 75–80MB，且把每个字重切成约一百个 unicode-range 文件；简体中文、繁体中文、日文与韩文加起来超过 270MB，而能绘制全部这些文字的单个 Noto Sans CJK 文件只有 16.5MB。

**把中日韩字体裁剪到品牌可能用到的字符。** 文件能小一个数量级。但裁剪即修改：若许可证保留字体名就必须改名，而且一旦客户名称用到裁剪范围外的字符就会被拒绝——正是本次改动要消除的失败。

**拉丁字母也用 Noto Sans CJK，只随附一个文件。** 无需第二个字体，也无需回退。但它的拉丁字形与 Inter 是不同的字体，而 lyness 字标与外壳本身的字体已在使用 Inter，这会改变所有拉丁字标的字形。

**每种语言各随附一个地区版中日韩字体。** 日文汉字与繁体字就能各自采用本地字形。但这是四个约 16MB 的文件，换来的只是部分字符的字形差异；有此需要的品牌可以用 `--font` 自行提供。

**把 OFL-1.1 加进宽松许可集合。** 生成器里改一行即可。但这会把上游刻意排除的许可证重新归类，且作用于所有依赖而非我们实际随附的这些文件，而这些字体根本不是 npm 依赖。

## Consequences

仓库多出 17MB 字体文件，`lyn-host-brand-fonts` 的每个发布副本也都带着它们。

汉字按简体中文字形绘制，因此日文或繁体中文名称可读，但不符合其本地书写习惯。阿拉伯文、希伯来文、泰文与印地文名称仍被拒绝；它们需要字体，以及经过验证的从右到左或复杂文字排版。

字距在换字体处中断；混排多种文字的字标取所用字体中最高的行框，因此其中的拉丁字母会比纯拉丁字标略小。

`scripts/gen-third-party-notices.ts` 与 `lefthook.yml` 的 pre-commit glob 成为本 fork 改动的上游文件，已登记在 `CUSTOM.md`。更换字体时，必须在同一改动中记录新的版本、来源与校验和。
