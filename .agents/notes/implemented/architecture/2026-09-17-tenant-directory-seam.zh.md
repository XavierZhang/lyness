# Agent Note：租户是一次目录查找，信任什么由传输层决定

Status: implemented

[English](2026-09-17-tenant-directory-seam.md) | 中文

## Problem

多租户从一个 harness 尚且回答不了的问题开始：这个部署服务哪些租户，以及这个请求属于哪一个。代码树里没有任何东西指称租户，因此后续每一层——按租户的配置、按租户的凭据、持久记录里的租户列——都没有可以挂靠的键。

答案必须同时满足仓库既有的三条约束。能力缝要么完整、要么就不是能力缝，因此只有定义而没有提供方与调用方的交付不成立。路由身份不能来自模型可见的输入：发起者作用域那篇笔记已经否决了让模型或工具参数选择 Session、租户或沙箱。托管相关的关注点不得扩散进与提供方无关的 API，因此现有的任何能力缝都不能新增 `tenantId` 参数。

## Decision

`ctx.tenants` 是一个提供三种查法的目录——调用方声明的不可变 id、请求到达的主机名、直接子域名携带的标识——每种查法对不认识的对象答复 `undefined`。`@lyness/lyn-tenant-static` 从组合配置提供租户清单，在加载时校验每一行，并拒绝两行争用同一个 id、标识或主机名。`@lyness/lyn-tenant-http` 消费该目录：应用解析顺序（先请求头，再主机名，最后子域名），在自己的路由上答复发起请求的一方属于哪个租户，并拒绝解析不到的请求。

租户 id 是不透明且不可变的，它既不是标识也不是主机名，因为这两者都是运营方会更改的呈现，而指称租户的持久记录必须始终可解析。

解析策略属于调用方，不属于能力缝。部署信任请求的哪一部分是传输层知识：`X-Tenant-ID` 在设置它的网关之后是权威的，在网关之前可被伪造。因此能力缝不表态，而第二个调用方——RPC 面、会话标记方——用自己的策略调用同一个已导出的 `resolveTenant`。

解析不到的请求会被拒绝。没有兜底租户，因为提供另一个组织的数据比什么都不提供更糟。

## Alternatives considered

**在 RPC 网关里解析。** 每个 Remote 调用到达时就已带上租户作用域。但网关在构造上就看不到请求头——它分发的是端点与载荷——因此租户只能在仍持有 `req.headers` 的浏览器连接路由里解析，而那是上游文件，本 fork 将在每次合并中承担它。推迟到确有 RPC 面需要租户时再做。

**用子域名作租户 id。** 少一层映射，每条记录里的 id 也可读。但重命名租户或把它迁到另一个域名，会让所有指称它的持久记录失效——workspace 的 id 之所以不用路径，正是为了避开这种失败。

**解析不到时回落到配置的默认租户。** 私有化部署将完全不需要配置主机名。但同一条规则在 SaaS 下，会把一个配错的域名变成静默地用另一个租户的数据来服务的请求。

**把解析顺序放进服务定义。** 所有调用方无需重复策略即可得到一致解析。但这个顺序是传输层知识，把它编码进与提供方无关的 API，等于把一个部署的信任模型强加给未来所有调用方。

**按需求文档提供 `/api/v1/tenant/config`。** 那是文档里写明的验收标准。冲突 #2 已裁决租户配置走 Typert RPC 而不是 REST；本路由只答复身份——id、标识、显示名——配置将遵循该 RPC 裁决。

## Consequences

不挂载本组任何内容的部署即单租户且毫无变化；能力缝是选配的，没有任何随附 bundle 组合它。

已解析的租户不会被带到答复之外。RPC 网关与会话日志将在各自需要时调用 `resolveTenant`，这也让租户不进入环境态——远程边界本就看不到那种状态。

租户清单在加载时固定，因此新增租户是改补丁层加重启，直到数据库支撑的目录替换掉静态那一行。

新增一个 `ctx` 服务要在若干生成器的表里手工登记——它所属的子系统页、其类型被记录在哪一页、能力缝角色，以及类型等价清单。这些表都没有扩展点，因此每一张都成为本 fork 改动的上游文件；`CUSTOM.md` 记录了它们，而它们指向的页面是 [docs/subsystems/multi-tenancy.zh.md](../../../../docs/subsystems/multi-tenancy.zh.md)。
