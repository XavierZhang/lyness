# Agent Note：部署品牌是组合层配置，按响应下发

Status: implemented

[English](2026-09-13-deployment-brand-as-composition-config.md) | 中文

## Problem

一个部署需要自己的视觉标识，而两个看起来最自然的位置都是错的，原因是同一个事实在那里会被决定两次。

第一个是用户设置。`settings.yaml` 层叠在组合**之上**，因此插件通过设置缝暴露的任何东西，都可以被使用该部署的人改写。而部署的标识恰恰是必须对这个人成立的那个事实。

第二个是构建。上游通过 `LYNESS_CLIENT_*` 前缀给自己打品牌，那些值在构建期嵌入浏览器产物——`LYNESS_CLIENT_TITLE` 是在客户端包里直接从 `process.env` 读出来的。这对只发行一个品牌的产品成立，却让每次换品牌都变成一次前端重新构建，而部署脚本做不到这件事。

## Decision

品牌值是一个**不注册任何设置段**的宿主插件的**组合层配置**，并且**作用于每一个 index 响应**，而不是编译进去。

`@lyness/lyn-host-brand-deployment` 承载产品名、品牌色与三个资产文件名，在加载时全部校验，提供资产，并把品牌写入每一次 index 渲染。`lyn-web-app` 以空配置挂载这一行，因此一个部署只需从它 profile 的 patch 层填充该行并重启，就完成了品牌化。

不注册设置段是机制，不是遗漏：设置缝把用户的段层叠在插件的入口配置之上，而一个不贡献任何段的插件，其组合层取值之上没有任何一层。

两种 index 机制之间的分工，取决于各自能表达什么。品牌对象与主题色是结构化注入行，因为注入行同时喂服务端 HTML 与 static worker 的启动载荷。标题与图标链接走 `tapIndex`，因为两者都是对随包 index 已声明的标记的**替换**，而注入行只能追加——第二个 `<title>` 会被忽略，第二个图标链接由浏览器而非部署来裁决。

## Alternatives considered

**把品牌放进 `settings.yaml`。** 它是仓库面向用户的配置文件，且不需要新增包。但它位于组合之上，因此使用该部署的人可以改掉产品名、换掉图标。对一个多租户部署来说，这恰恰是被购买的那项属性。

**扩展构建期的 `LYNESS_CLIENT_*` 路径。** 这是上游已经在用的机制，客户端读这些值完全不需要服务端参与。但此后每个品牌都需要自己的一次前端构建，部署脚本因此改不动标题；而一个同时服务多个品牌的托管部署会需要多套产物。

**接受上传，按租户存资产。** 这是需求文档要求的，也是唯一能让租户自助换 logo 的做法。但它会造出接收路由、服务端格式校验，以及由运营方投放文件本可以完全消除的跨租户执行面；这笔账为何这样算，记在[两层划分](../../../../.fork/BRAND-CONFIG.md)里。

**整个 head 都走 `tapIndex`。** 只有一种机制而不是两种，所有值都以同一方式到达服务端页面。但它会让品牌对象与颜色够不着 static worker 形态，那种形态只消费结构化注入行——能做成注入行的就应该是注入行。

## Consequences

资产按角色寻址，而非按文件名：名为 `logo.svg` 的 favicon 以 `/brand/favicon.svg` 提供。因此请求不会把任何路径片段带进文件读取，遍历栅栏无物可栅，而未配置的角色返回 404 而不是变成一次探测。

每一处配置错误都会让加载失败——命名了资产却无目录、目录是相对路径、文件不存在、扩展名无法提供、颜色既非十六进制三元组也非关键字。品牌配错的部署不会启动，而不是去提供一个品牌已悄然回落的页面。

仍有两个事实存在第二个归属地。`AppFrame` 从构建期取值读取它界面内的产品标题，因此在出现一个读取已发布品牌的客户端占位方之前，服务端标题与界面内标题可能不一致。另外 static worker 形态的部署会失去标题与图标，因为那两者是 tap。

图标与字标的 URL 已发布，但尚无任何东西绘制它们；客户端插槽占位方属于独立工作，也正是 fork 剩下那项品牌资产任务所需要的。
