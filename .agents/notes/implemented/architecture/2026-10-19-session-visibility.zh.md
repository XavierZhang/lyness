# Agent Note: 一次调用看得到谁的对话

Status: implemented

[English](2026-10-19-session-visibility.md) | 中文
## Problem

[会话归属](../../proposed/architecture/2026-10-07-session-ownership.zh.md)记下了谁开启了一场对话，却没有任何东西把它读回来。于是一套服务有名有姓的人的部署，把每个会话都正确地归了属，同时仍然让这些人各自能列出、打开、搜索、翻页、跟随并读取别人会话的投影——记录在那儿，而产品的行为和键盘前只坐着一个操作者时一模一样。

## Decision

`ctx.sessionVisibility`，也就是 `lyn-session-ownership` 的 `./visibility` 那一半，回答进行中的这次调用是否看得到某一场对话；Remote 会话界面在四个地方问它：`session/list` 与 `session/search` 共用的那次语料读取、每个由 Agent 支撑的端点所经的那次解析、历史的观察，以及投影读取。

规则是对「读到的归属」所作的一个函数：

- 没有 principal 的调用看得到全部。CLI、子智能体、定时跟进与入站 webhook 都是部署在对自己行事；过滤它们等于让一套部署看不见自己做过的事。
- 一场对话属于开启它的那个人，不属于别人。管理一套部署不等于读它的人的对话，所以没有任何角色能把这一条放宽。
- 没有归属、但其父会话正开着的对话，属于那位父会话的归属人。子智能体会话由循环开启而不是由请求开启，所以它不带归属；这条血缘最多走八跳，而没开着的父会话不会为了回答这个问题被唤起。
- 其余没有归属的对话都是部署自己的，只有平台管理员看得到。那是唯一能为「部署自己做的事」负责的身份，也让定时与 webhook 的工作仍然够得着。

被拒绝的会话答 `session/not-found`，而不是一个专门的拒绝码，于是一个人没法靠 id 把另一个人的对话枚举出来。

读取保持廉价。活跃会话用它自己的投影作答；冷的翻页或跟随用观察已经持有的那些事件作答；列表用持久投影缓存作答——这需要两个新的宿主专用读面：`sessionProjections.checkpointState(checkpoint, key)` 与 `sessionProjectionCache.cachedCheckpoint(meta)`，因为缓存原有的读面只服务客户端可见的单元，而归属刻意不是其中之一。缓存里没有归属的那一行读作「没有归属」：它不出现在普通成员的列表里，而不是被泄漏出去；按 id 打开它时，仍然去问那个会话自己的日志。

规则是一行编排。`module-accounts` 把它与写入那半并列选上；没有账户的部署两者都不挂，也就什么都不过滤。

## Alternatives considered

**在每个端点里过滤。** 一个控制器里十三处检查，下一个控制器里漏掉一处。两个解析面、那次语料读取、历史的 `sourceFor` 与投影读取，本就是每个端点都会经过的汇聚点，所以规则落在「Session 被解析出来」的地方，而不是「它被请求」的地方。

**像授权规则那样在 Gateway 里执行。** Gateway 按端点声明的身份授权；它并不知道哪个参数点名了一个会话，而一个列表压根没有单一主体。用声明点出主体字段，对逐个会话的端点可行，列表与搜索仍要靠过滤——本来一种机制，变成两种。

**把归属发布成一个 wire 投影。** 那会让列表读取变得很省事，因为投影缓存服务的正是客户端可见单元。它同时也把归属放上了线，发给一个用不着它的客户端，再由写它的宿主读回来。两个宿主专用缓存读面只花两个小方法，并且把归属留在做判断的地方。

**让平台管理员读得到全部。** 对支持工作很诱人，也是个错误的默认：一套部署的管理员通常是客户自己的员工，而「管理员能读你的对话」是一条必须被刻意选择、而不能从「他能配置登录」继承而来的性质。管理员仍然看得到部署自己做过的事。

**用 forbidden 之类的码拒绝。** 那等于告诉调用者这个 id 存在。not-found 对这个调用者既是真话，也不多说一个字。

## Consequences

有账户的部署现在在每一次 Remote 读取上都把人与人的对话分开，而单操作者安装不受影响，因为那里根本不挂这条规则。会话列表对每个冷行多一次缓存读取。

Workspace 投影也会问，而它是唯一一个「共享而非归属」的界面：Workspace 是 Host 上的一个目录，它的注册因此保持共用，而记在它名下的对话按读取方收窄——baseline、每条 `upsert`，以及注册表全局的归档与置顶集合。账目本身不动，收窄的只是发出去的东西，并且一帧只读一次语料库。它的命令也拒绝投影所隐藏的东西——归档、置顶和重排都是只需一个 id 的写入——各自沿用它对「无法计入账目的 Session」已有的措辞；两个幂等的移除则原样作答而不是拒绝，于是没有任何一个动词会告诉某个人「另一个人的对话存在」。一代 `follow()` 比开启它的那次请求活得更久，因此它捕获那个 principal，并通过 `requestPrincipal.as()` 在每帧重新进入，而不是以「恰好共用同一任务的那次调用」的身份作答。挂载了规则却没有组合 `sessionQuery` 的部署会在第一份投影处被拒绝，而不是不收窄地发出去。

有两个读取方按原样问不到这条规则，各自拿到了它需要的东西。`session_query` 工具改问它的 Agent 正在运行的那场对话：`mayReadFrom(reader, target)` 以那场对话的归属人作判定，于是一次工具调用够得到开启它的人够得到的，其余的用「工作区之外」那同一句话拒绝。`/export` 的 ZIP 路由和别的地方一样，按进行中的那次调用问——前提是让每请求作用域像包裹解码调用那样去包裹一条精确 Fetch 路由：一次注册，两条路径，而不是再造一种发布 principal 的办法。发问者导不出的会话，答法与根本不存在的会话一样。

父会话没开着时，子智能体会话对它的归属人不可见，直到父会话再次打开。另一条路是为了决定要不要显示一个子会话而唤起它的父会话，那会把一次读取变成一次激活。
