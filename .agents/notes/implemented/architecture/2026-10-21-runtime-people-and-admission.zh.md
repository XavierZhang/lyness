# Agent Note: 加一位同事，不用改服务器上的文件

Status: implemented

[English](2026-10-21-runtime-people-and-admission.md) | 中文
## 问题

带账户的部署从 composition 里读它的人：名册在 `people/static`，被准入为这些人的目录身份在 `admission-roster`。两者都是配置，于是加一位同事意味着改服务器上的一个文件再重启它——而要做这件事的是客户自己的管理员，他在那台机器上没有 shell。登录渠道早就改成了运行时记录，依据是[账户模块自己的那个决定](../../proposed/architecture/2026-10-15-diverging-from-the-single-operator-host.zh.md)，而且也写明了：渠道可以不发布就加上，但在有人手工改名册之前，没人能经由它登录。

## 决定

人员与准入绑定变成由管理员维护的持久记录，与 composition 写下的那些并存，并且写下的那一半优先。

`@lyness/lyn-managed-people` 在自己的 domain 里持有存储的那一半，并在同一处回答两个 seam：`./directory` 提供 `ctx.people`，`./admission` 提供 `ctx.signInAdmission`，两者读取的 `people` / `bindings` 配置与各自的静态对应物完全相同，并把每次查找转发给 `ctx.managedPeople`。已经写好名册的安装原样保留；`module-accounts` 改的只是这两行指名哪个插件。

composition 仍然写下第一个人，并且名册不得为空：空系统里没有管理员来添加第一个管理员，而那个写下的人也是「最后一个存储的管理员被移除」之后的恢复路径。对写下的人或绑定的修改以 `written` 被拒绝，而不是被接受，因为下一次启动会重新读那个文件，而界面已经报告了一件不真实的事。

本服务施加的那些规则，每一条都是因为否则会有某条路径可达：

- 授予一个角色就是授予它能做的事，所以租户管理员造不出平台管理员——那个身份管理每一个组织，包括他管不到的那些。
- 一次修改既按提交内容授权，也按已存储的记录授权，否则一个租户的管理员只要用自己的组织报出另一个租户的人员 id，就能把人夺走。
- 一条绑定由「人」**与**「渠道」共同授权，渠道归属读自已配置的渠道记录（当部署存储它们时）：绑定到另一个组织的目录上，就等于让那个组织的人能在这里登录。
- 成员身份 id 只由人的 id 推出，因此改某人的角色不会移动一个已打开会话所记的成员身份 id。
- 被移除的人连同他的 id 一起退场，于是他开过的对话仍归属于一个不再登录的人，而不会归到下一个被添加的人头上。

`@lyness/lyn-api-people-controller` 把它投影到 `people` Remote 命名空间上，自己不做任何判定：解析这次调用所处的身份、交给服务、再把每种拒绝按自己的错误码汇报。`@lyness/lyn-client-ui-settings-people` 是那个 Settings 页面，挨着登录渠道那一页。

## 考虑过的替代方案

**首次启动时用配置给存储做种。** 运行时只有一个真相来源，文件退化成引导。但这也意味着运维之后再改那个文件时什么都不会发生，而这正是仓库规则要防的那种「静默配置失效」。分层叠加让文件对它所指名的东西保持权威。

**允许存储遮盖一个写下的人。** 对「从界面上改掉名册里的错别字」很诱人，但是错的：composition 每次启动都会重新读，于是那条存储记录只在没人重启之前算数。

**取代 `people/static` 与 `admission-roster`。** 对不想要运行时管理的部署，它们仍然是对的答案；删掉它们就等于强迫一个只有一个运维、一个文件的安装去用存储。

**把管理 API 放到 `PeopleDirectory` 上。** 那样界面就能直接有 `list()`，不需要第二个服务。但目录是一个 Service Definition，每个问题一个抽象读；一个无法写入的 provider——比如 SSO 目录——就得去拒绝三个它本不该有的方法。

**绑定只按「人」授权。** 更简单，但会留下「租户管理员把另一个组织的目录主体准入成自己的用户」这条路。渠道检查的代价是一次 list 调用，走的还是那条已经在决定「谁管得着哪个渠道」的规则。

## 后果

管理员添加一位同事、准入他的目录身份，这个人就能登录了——不需要 shell、不需要文件、不需要重启。渠道来自 composition 而不是记录的部署，无法把绑定权下放给租户管理员，因为渠道检查读的是存储；这是 fail-closed，并写在该包的「已知限制」里。

一个人仍然只在一个组织里持一个身份，和写下的名册一直以来的做法相同。移除某人不会结束他已经建立的会话，也没有任何东西阻止最后一个存储的管理员被移除——写下的名册正是这件事可恢复的原因。

在建第二个 Settings 页面的过程中，`messageOf` 被收归到 `lyn-client-store`，因为两个页面汇报载体层拒绝的方式完全相同。两个页面其余共享的东西是形状而不是实质——它们的词汇一个是渠道、一个是人员——因此标注为「刻意保持平行」，而不是硬压进一个必须同时指名两者的基类。
