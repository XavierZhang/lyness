# Agent Note：跨上游同步重新生成品牌改名

Status: implemented

[English](2026-09-12-regenerating-the-rebrand-across-an-upstream-sync.md) | 中文

## Problem

改名后的第一次上游同步跨越 2151 个提交，从 0.1.2-alpha.1 到 0.1.5-rc.1。上游改了 8274 个文件，其中 806 处改名；fork 改了 6015 个，几乎全部是改名产物。两套互不知情的改名在同一棵树上做逐行合并，会产生数以千计的冲突，并在双方都移动过的路径上留下重复目录。

codemod 的 `--reverse` 方向救不了场。规则不是双射：三个源映射到同一个 scope，而改写转义正则的那几条规则反向会把 `(?:-|$)` 当字面文本插进源码。

## Decision

**不要合并改名，重新生成它。**

真实的 fork 差异是测出来的，不是假设的：把 codemod 应用到 merge-base 的树上，再与 fork 分支对比，只剩 27 个文件，其中 20 个可再生成（文档目录、声明文件、lockfile、snapshot）。只有 5 个文件带着任何生成器都产不出的改动。

因此同步整体取上游的树，再在其上重建 fork：

1. `git merge -s ours --no-commit` 记录双亲，使下次同步能算出正确的 merge base。
2. `git read-tree -u --reset upstream/master` 把索引与工作树换成上游的。
3. fork 独有文件从备份恢复，5 个补丁重打。
4. `rebrand --apply` 重新生成全部改名。

这条路成立，只因为 codemod 可重放且幂等。让 fork 能持续跟上上游的是这个性质，而不是改名本身。

## Alternatives considered

**逐行合并。** 上游改了 8274 个文件、含 806 处改名，而 fork 自己也改名了 86 条路径。到这个规模 git 的改名检测会放弃，双方的移动都退化为新增与删除，每个被改名的目录都会出现两份。冲突数以千计，而其中没有一条是需要人做的决定：改名是可推导的。

**先反向回退改名，合并，再重放。** `--reverse` 是为查看而存在的，而 fork 分支足够小，回退后合并会很轻松。但它不能用于此处：多条规则共享同一个目标，反向时必须猜名字来自哪个源；而改写转义正则的那几条规则会把 `(?:-|$)` 当作字面文本写进源文件。建立在有损逆映射上的合并，会把破坏藏进 6000 个文件里。

**用 `-X theirs` 解冲突。** 一条命令，剩下的品牌残留交给 codemod 归一。但它会静默丢弃落在冲突 hunk 里的每一处 fork 改动，而 fork 仅有的几处真实改动正好在那里——遥测默认值所在的段落恰恰是上游本轮重写过的。静默丢掉 fork 赖以存在的那些改动，是所有失败方式里最坏的一种。

**从上游拉新分支，再把 fork 重新应用上去。** 能得到同样的树，过程还更省事。但它产出的提交只有一个父，于是下次同步会拿 fork 的旧历史去算 merge base，把整段分歧重新发现一遍。祖先关系才是值得保留的部分。

## Consequences

codemod 暴露出四处缺陷，每一处从首次运行起就一直是错的。

**`scoped-directory-fragment` 从未匹配成功。** 它排在 `scope-bare` 之后，而后者会单独改写 scope 片段；等它运行时，它的源文本已经不存在了。于是形如 `join(modules, '@scope', 'product-name')` 的路径保留了旁边 manifest 已经去掉的产品段，指向一个不存在的包。现已前移到所有 scope 规则之前。**一条报告零匹配的规则是待查的缺陷，而不是无事可做的规则。**

**二进制判定拒绝了两个源文件。** 首块中的 NUL 字节是 `git diff` 的判据，而两个测试夹具在字符串字面量里嵌了真实的 NUL。两者都冻结在上游名字上，其中一个 import 了一个不再存在的包。现在改为判断整个文件是否能以 UTF-8 解码——这恰好就是改写能够无损往返的条件。同一个假设还把 NUL 用作归档引用的占位符；该规则现改为只作用于引用之间的片段，不再保留任何字符。

**记录这次改名的笔记被改名改坏了。** 一篇以改名为主题的文档必须引用上游写法，于是 codemod 把它记录的每条规则都变成了 `X becomes X`。这类文档——台账、需求文档、codemod 本身，以及现在这篇记录——已纳入保护。

去掉包名中的产品段，代价还在持续。上游正是靠那一段把自家包与重命名过的 vendored 包分开，`@lyness/<name>` 做不到。这次同步又带来三处需要手工排除的名字前缀检查，其中一处是**失效开放**的——用模板拼出的前缀得到一个没有任何包匹配的字符串，检查通过了，却什么也没验证。排序夹具同样受影响，新名字的字典序与旧名字不同。

三个测试在本机失败。三者都是上游新增代码，且在未改名的纯上游检出上以完全相同的方式失败，因此属于上游与这台机器，不属于本次同步。
